# Модель прав доступа

Документ описывает роли, разрешения, область данных и журнал аудита (ТЗ, п. 2, п. 8.3). Решения и их причины — ADR-009 в `docs/spec/decisions.md`.

## Принципы

1. **Проверка на сервере.** Каждый эндпоинт API, кроме входа, обновления сессии и `GET /api/health`, требует действующего access-токена и проверяет разрешения. Скрытие пунктов меню в интерфейсе — только удобство.
2. **Минимум прав по должности.** Роль даёт только то, что нужно для работы. Доступ к конфиденциальным данным выдаётся отдельно, с основанием.
3. **Никаких действий над собой.** Администратор не меняет собственные роли, разрешения, блокировку и пароль через администрирование: это делает другой администратор. Свой пароль пользователь меняет через «Сменить пароль».
4. **Всё значимое — в журнал.** Вход, выход, неудачные попытки, блокировки, изменения учётных записей, прав и настроек пишутся в `audit_logs` в той же транзакции, что и само изменение.

## Конфиденциальные разрешения

`diagnostics.answers.read` и `research.personal_data.read`:

- не входят в роли администратора и исследователя (п. 2.1, 2.4 ТЗ);
- выдаются только индивидуально в карточке пользователя с обязательным основанием (например, номер приказа) и необязательным сроком действия;
- не выдаются самому себе;
- выдача и отзыв записываются в журнал аудита с основанием.

Кто, кроме преподавателей, может получать эти разрешения и по какому документу, решает колледж (open-questions, вопросы 5 и 6).

## Область данных (FR-002)

`AccessScopeService` (`apps/api/src/auth/access-scope.service.ts`) возвращает область данных пользователя:

- `all` — все группы, если есть `groups.manage` (администратор справочников);
- `assigned` — группы и дисциплины из действующих закреплений преподавателя в `teacher_assignments` (дата начала наступила, дата окончания не задана или ещё не наступила).

Сервисы модулей (студенты, диагностика, ИОТ, мониторинг, аналитика) фильтруют запросы по этой области.

Применение на этапе 04:

| Данные                          | Администратор (`all`)                  | Преподаватель (`assigned`)                                     |
| ------------------------------- | -------------------------------------- | -------------------------------------------------------------- |
| `GET /api/groups`               | все группы                             | группы из своих закреплений                                    |
| `GET /api/disciplines`          | все дисциплины, группы и преподаватели | свои дисциплины и только свои группы в них                     |
| `/api/students`                 | нет доступа (нет `students.read`)      | студенты, текущая группа которых входит в его закрепления      |
| Добавление, импорт, перевод     | нет доступа                            | только в свои действующие группы                               |
| Чужой студент по идентификатору | —                                      | 404 «Студент не найден» (существование записи не раскрывается) |

Студент, исследователь и администратор получают 403 на списки студентов. Учётные записи студентов администратор может только блокировать и сбрасывать им пароль в «Администрировании» (ADR-010). Студент видит только собственные данные: эндпоинты кабинета берут идентификатор студента из сессии, а не из параметров запроса.

Применение на этапе 05 (профиль студента):

| Данные                                      | Кто получает          | Ограничения                                                                                                                |
| ------------------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/students/:id/profile`, `/history` | `students.read`       | студент из области данных, иначе 404                                                                                       |
| `GET /api/students/:id/observations`        | `students.read`       | все наблюдения о студенте, включая служебные; видят все преподаватели, которым доступен студент                            |
| `POST /api/students/:id/observations`       | `observations.manage` | студент из области данных; дисциплина — только та, которую автор ведёт в группе студента                                   |
| `PATCH /api/students/:id/observations/:oid` | `observations.manage` | только автор наблюдения (иначе 403)                                                                                        |
| `GET`, `PATCH /api/cabinet/profile`         | `cabinet.access`      | студент по учётной записи из сессии; наблюдения — только с видимостью `STUDENT_VISIBLE` (FR-016); меняются только интересы |

Служебные наблюдения (`INTERNAL`) не передаются студенту ни через один эндпоинт: эндпоинты сотрудников ему недоступны (403), а кабинет отбирает наблюдения по видимости на сервере. Текст наблюдения не пишется в журнал аудита — журнал читает администратор (п. 2.1 ТЗ); в журнал попадают идентификатор, студент и видимость.

Применение на этапе 06 (конструктор методик, ADR-012):

| Данные                                                      | Кто получает         | Ограничения                                                                                    |
| ----------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------- |
| `/api/questionnaires/**`, `/api/diagnostic-directions/**`   | `diagnostics.manage` | общий справочник без ограничения областью данных; администратор, исследователь и студент — 403 |
| `PUT`, `DELETE /api/questionnaires/:id/versions/:versionId` | `diagnostics.manage` | только черновик неархивной методики (иначе 409); опубликованную версию защищают и триггеры БД  |

В журнал аудита пишутся действия с методиками (`questionnaire.*`, `questionnaire_version.*`, `diagnostic_direction.*`) с номером версии и названием, без текстов вопросов.

Применение на этапе 07 (проведение диагностики, ADR-013):

| Данные                                                           | Кто получает                                      | Ограничения                                                                                                               |
| ---------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `GET`, `POST /api/diagnostic-assignments`, `GET /:id`, `/cancel` | `diagnostics.manage`                              | группы и студенты из области данных; в счётчиках и списке прохождений — только доступные студенты; чужое назначение — 404 |
| `GET /api/diagnostic-sessions/:id/form`, `POST /:id/paper`       | `diagnostics.manage`                              | студент прохождения из области данных, иначе 404                                                                          |
| `GET /api/diagnostic-sessions/:id/answers`                       | `diagnostics.answers.read`                        | исходные ответы и ревизии; у администратора разрешения нет (п. 2.1); студент из области данных                            |
| `POST /api/diagnostic-sessions/:id/corrections`                  | `diagnostics.manage` и `diagnostics.answers.read` | только завершённое прохождение; причина обязательна                                                                       |
| `GET /api/students/:id/diagnostics`                              | `students.read`                                   | баллы и уровни действующей ревизии; студент из области данных, иначе 404                                                  |
| `/api/cabinet/diagnostics/**`                                    | `cabinet.access`                                  | только прохождения студента из сессии (чужое — 404); форма без значений и ключей; результат — только текст для студента   |

Действия журнала аудита этапа 07: `diagnostic_assignment.created`, `diagnostic_assignment.cancelled` (с причиной), `diagnostic_session.completed`, `diagnostic_session.paper_entered`, `diagnostic_session.corrected` (с причиной). Содержание ответов в журнал не пишется.

## Сессия и вход

| Механизм                          | Значение по умолчанию | Где задаётся                       |
| --------------------------------- | --------------------- | ---------------------------------- |
| Срок жизни access-токена          | 15 минут              | `JWT_ACCESS_TTL_SECONDS` (`.env`)  |
| Срок сессии (refresh-токен)       | 7 дней от входа       | Настройка `auth.sessionDays`       |
| Неудачных попыток до блокировки   | 5                     | Настройка `auth.maxFailedAttempts` |
| Длительность временной блокировки | 15 минут              | Настройка `auth.lockoutMinutes`    |
| Минимальная длина пароля          | 10 символов           | Настройка `auth.passwordMinLength` |
| Запросов входа с одного IP        | 20 в минуту           | `LOGIN_RATE_LIMIT` (`.env`)        |

Значения по умолчанию приняты до ответа заказчика (open-questions, вопрос 8).

Ответы входа: неверный логин и неверный пароль дают одинаковое сообщение «Неверный логин или пароль» (401); временная блокировка — 423 с указанием, через сколько минут повторить; учётная запись, заблокированная администратором, — 403 (сообщается только после верного пароля).

## Журнал аудита

Таблица `audit_logs` защищена триггером от изменения и удаления. Коды действий этапа 03:

| Код                       | Событие                           |
| ------------------------- | --------------------------------- |
| `auth.login`              | Вход                              |
| `auth.logout`             | Выход                             |
| `auth.login_failed`       | Неверный пароль                   |
| `auth.locked`             | Временная блокировка входа        |
| `auth.password_changed`   | Смена пароля пользователем        |
| `user.created`            | Создание учётной записи           |
| `user.updated`            | Изменение ФИО или e-mail          |
| `user.blocked`            | Блокировка (с причиной)           |
| `user.unblocked`          | Разблокировка                     |
| `user.password_reset`     | Сброс пароля администратором      |
| `user.roles_changed`      | Изменение ролей                   |
| `user.permission_granted` | Выдача индивидуального разрешения |
| `user.permission_revoked` | Отзыв индивидуального разрешения  |
| `settings.updated`        | Изменение системных настроек      |

Модули следующих этапов добавляют свои коды (ИОТ, диагностика, профили, экспорт) в формате `<сущность>.<действие>`.

## Персональные данные в журналах

Журнал приложения (pino) не содержит ПДн (п. 8.3 ТЗ):

- поля `login`, `lastName`, `firstName`, `middleName`, `fullName`, `email`, `phone`, `iin`, пароли, токены, cookie и заголовок `Authorization` заменяются на «[скрыто]»;
- в строках заменяются адреса e-mail, номера телефонов и ИИН;
- журнал запросов содержит метод, шаблон маршрута без query-параметров, статус, длительность и идентификатор пользователя;
- тело запроса в журнал не пишется; клиент при ошибке 500 получает общее сообщение без подробностей.

Проверка — `apps/api/test/logging.e2e-spec.ts`, `apps/api/src/logging/mask.spec.ts`.
