# Архитектурные решения (ADR)

Формат записи: контекст → решение → последствия. Решения из `CLAUDE.md`, п. 2, меняются только по согласованию с заказчиком.

## ADR-001. Backend — NestJS (ESM)

- **Контекст.** ТЗ (п. 8.1) допускает Laravel или NestJS. Frontend на TypeScript, нужны общие типы и схемы валидации.
- **Решение.** NestJS + TypeScript, REST, OpenAPI через `@nestjs/swagger` (`/api/docs`, JSON — `/api/docs/openapi.json`). Используется NestJS 12, который распространяется только как ES-модули, поэтому `apps/api` — ESM-пакет (`"type": "module"`, `module: nodenext`, относительные импорты с расширением `.js`).
- **Последствия.** Один язык во всём монорепо; общий пакет `@iot/shared`. Jest запускается в режиме ES-модулей (`node --experimental-vm-modules`, `ts-jest` с `useESM`).

## ADR-002. ORM — Prisma, СУБД — PostgreSQL 16

- **Контекст.** ТЗ (п. 7) требует PostgreSQL; нужны воспроизводимые миграции (NFR-007) и расширяемая схема (NFR-009).
- **Решение.** Prisma 7 (`prisma.config.ts`, генератор `prisma-client`), миграции в `apps/api/prisma/migrations`. Имена таблиц п. 7 ТЗ задаются через `@@map`.
- **Последствия.** Миграции применяются командой `prisma migrate deploy` при обновлении без потери данных. Переменные окружения Prisma читает из корневого `.env` (или файла из `ENV_FILE`).

## ADR-003. Демо-методики вместо методик исследования

- **Контекст.** Тексты, ключи и правила интерпретации методик Т. А. Ильиной, А. А. Реана, В. И. Моросановой передаёт заказчик (п. 4.4, огр. 1). На момент разработки они не переданы.
- **Решение.** До передачи используется демо-методика с пометкой «ДЕМО — не для исследования» в названии и источнике. Реальные методики вносятся через конструктор или сид-файл; правильность расчёта подтверждается контрольными примерами (п. 11.3).
- **Последствия.** Содержание реальных методик не выдумывается; демо-данные нельзя использовать в исследовании.

## ADR-004. Монорепозиторий pnpm

- **Контекст.** Frontend, backend и общие типы развиваются вместе.
- **Решение.** pnpm workspaces: `apps/api`, `apps/web`, `packages/shared`. Пакет `@iot/shared` — ESM; для Node.js (API) экспортируется собранная версия `dist/`, для Vite (web) — исходники `src/` (условие экспорта `node`). Корневые скрипты `typecheck`, `test`, `dev` сначала собирают `@iot/shared`.
- **Последствия.** Изменения общих типов видны обоим приложениям без публикации пакетов.

## ADR-005. Версии инструментов

- **Контекст.** На момент инициализации (октябрь 2026) вышел TypeScript 7 (нативный компилятор), но `typescript-eslint` и `ts-jest` поддерживают TypeScript < 6.1 / < 7.
- **Решение.** TypeScript закреплён на `~6.0.3`. Целевая версия Node.js — 24 LTS (`.nvmrc`), поле `engines` допускает `>=24`.
- **Последствия.** Переход на TypeScript 7 — после поддержки его инструментами линтинга и тестирования.

## ADR-006. Окружения и базы данных

- **Контекст.** NFR-010 требует разделения тестовой и рабочей среды.
- **Решение.** Окружения `development`, `test`, `production` с отдельными файлами `.env`, `.env.test`, `.env.production` (в репозитории только `.env.example`). В dev-окружении `docker-compose.dev.yml` поднимает PostgreSQL 16 с базами `iot_dev` и `iot_test`.
- **Последствия.** Автотесты никогда не работают с базой разработки или рабочей базой.

## ADR-007. Модель данных: ревизии диагностики, снимки ИОТ, неизменяемость на уровне БД

- **Контекст.** ТЗ требует неизменяемости исходных ответов (FR-013), версионирования методик без пересчёта старых результатов (FR-026), хранения предыдущих версий ИОТ (FR-043) и журнала аудита (п. 8.3).
- **Решение.**
  - Содержание методики хранится в версиях (`questionnaire_versions` и дочерние таблицы); опубликованная версия не редактируется.
  - Результаты диагностической сессии организованы по ревизиям (`diagnostic_revisions`): исправление ввода и пересчёт добавляют новую ревизию ответов и показателей с причиной, прежние строки остаются.
  - Текущее содержимое ИОТ редактируется в `trajectories`/`trajectory_stages`, а каждая утверждённая или скорректированная редакция фиксируется неизменяемым JSON-снимком в `trajectory_versions`. Так идентификаторы этапов, на которые ссылаются задания и комментарии, остаются стабильными.
  - Таблицы `diagnostic_answers`, `diagnostic_scores`, `diagnostic_revisions`, `motivation_profile_history`, `trajectory_versions`, `audit_logs` защищены триггером `forbid_modification` (запрет `UPDATE`/`DELETE`).
  - Идентификаторы — UUID v7. Сгенерированный клиент Prisma не хранится в репозитории и создаётся командой `prisma generate` (перед сборкой, проверкой типов и тестами).
  - Prisma 7 работает через драйвер-адаптер `@prisma/adapter-pg`.
- **Последствия.** Защита от изменения истории не зависит от корректности кода сервисов. Ошибки триггера приходят с кодом `restrict_violation`; сервисы должны преобразовывать их в понятные пользователю сообщения (NFR-005).

## ADR-008. UI-библиотека — PrimeVue 4.5 (MIT), без перехода на PrimeVue 5

- **Контекст.** План (CLAUDE.md, п. 2) закрепляет PrimeVue. Начиная с версии 5.0 (июль 2026) PrimeVue распространяется под коммерческой лицензией PrimeUI: бесплатная Community License доступна только организациям с числом сотрудников менее 10 и требует ежегодно продлеваемого лицензионного ключа; без ключа библиотека показывает уведомление о лицензии. Колледж под эти условия не подпадает.
- **Решение.** Используется последняя версия под лицензией MIT: `primevue@4.5.5`, `@primeuix/themes@2.0.3`, `primeicons@7.0.0`. Версии зафиксированы точно (без `^`), чтобы обновление зависимостей не перевело проект на PrimeVue 5. Тема — пресет Aura, переопределённый тёмно-синей палитрой (`apps/web/src/theme/preset.ts`); собственные дизайн-токены — CSS-переменные `--iot-*` (`apps/web/src/theme/tokens.css`, `docs/design/tokens.md`). Тёмная схема отключена (ТЗ, п. 6.1). Шрифт — системный, без загрузки из интернета (работа в локальной сети колледжа).
- **Последствия.** Исправления безопасности для ветки 4.x могут прекратиться; на этапе 19 (`pnpm audit`) и перед передачей нужно проверить состояние ветки. Переход на PrimeVue 5 возможен только после согласования лицензии с заказчиком. Общие компоненты (StatusBadge, EmptyState, ErrorState, MetricCard, ProgressIndicator) написаны без зависимости от внутренних API PrimeVue, что упрощает возможную замену библиотеки.

## ADR-009. Авторизация, права доступа и журнал аудита

- **Контекст.** Этап 03: безопасный вход, разграничение прав на сервере (ТЗ, п. 2, п. 8.3), журнал изменений, маскирование персональных данных в журналах. Требования п. 2.1 и 2.4: администратор не получает доступа к диагностическим ответам по должности, исследователь — к персональным данным.
- **Решение.**
  - Сессия: access-токен JWT (HS256, 15 минут, хранится только в памяти браузера) и refresh-токен в cookie `iot_refresh` (httpOnly, SameSite=Strict, Secure в production, путь `/api/auth`). В БД хранится только SHA-256 хеш refresh-токена; при каждом обновлении токен ротируется. Срок сессии задаётся настройкой `auth.sessionDays` и отсчитывается от входа. Пользователь, роли и права читаются из БД при каждом запросе, поэтому блокировка, выход и отзыв прав действуют сразу.
  - CSRF: double submit (cookie `iot_csrf` + заголовок `x-csrf-token`) для запросов, которые аутентифицируются cookie: обновление сессии и выход. Остальные запросы передают access-токен в заголовке `Authorization`, который браузер не подставляет сам.
  - Пароли: argon2id (пакет `argon2`), политика — длина из настройки `auth.passwordMinLength`, буквы и цифры, без логина. Временный пароль выдаётся при создании учётной записи и сбросе; до его смены сервер отвечает 403 на всё, кроме смены пароля, `me` и выхода.
  - Перебор паролей: временная блокировка учётной записи после `auth.maxFailedAttempts` неверных паролей подряд на `auth.lockoutMinutes` и ограничение частоты запросов входа с одного IP (`LOGIN_RATE_LIMIT` в минуту). Ограничение частоты реализовано собственным guard (`apps/api/src/auth/login-rate-limit.guard.ts`): `@nestjs/throttler` 6.x распространяется как CommonJS и не загружается в Jest вместе с ESM-сборкой NestJS 12 (ошибка `require(esm)` в цикле). При переходе на несколько экземпляров API счётчики нужно вынести в общее хранилище.
  - Права: каталог ролей и разрешений — в `packages/shared/src/auth.ts`; при запуске API он синхронизируется с таблицами `roles`, `permissions`, `role_permissions`. Системные роли в интерфейсе не редактируются. Сверх ролей пользователю выдаются индивидуальные разрешения с основанием и необязательным сроком (`user_permissions`). Конфиденциальные разрешения (`diagnostics.answers.read`, `research.personal_data.read`) не входят в роли администратора и исследователя и выдаются только индивидуально. Действия администратора над собственной учётной записью (роли, разрешения, блокировка, сброс пароля) запрещены — так администратор не может выдать доступ к конфиденциальным данным самому себе.
  - Проверка прав: глобальный guard (`apps/api/src/auth/auth.guard.ts`) требует входа для всех эндпоинтов, кроме помеченных `@Public()`, и проверяет `@RequirePermissions()`. Область данных преподавателя (FR-002) вычисляет `AccessScopeService` по действующим закреплениям `teacher_assignments`.
  - Аудит: `AuditService.log()` вызывается в той же транзакции, что и изменение; автор и IP берутся из контекста запроса (AsyncLocalStorage). Пароли, токены и хеши в журнал не попадают.
  - Журналы: pino; все сообщения проходят маскирование (`apps/api/src/logging/mask.ts`): поля с ПДн и секретами скрываются по имени, e-mail, телефоны и ИИН — по шаблону. В журнал запросов пишется шаблон маршрута без query-параметров.
  - Ошибки API: единый формат `{ statusCode, message, fields? }` на русском (`apps/api/src/common/http-exception.filter.ts`); ошибки Prisma (уникальность, внешний ключ, неизменяемая запись) переводятся в понятные сообщения.
  - Интерфейс: пункты меню без нужного разрешения скрываются, порядок остальных сохраняется; по прямой ссылке раздел показывает «Нет доступа». Формы — VeeValidate и zod; используется `zod@3.25`, потому что `@vee-validate/zod` 4.15 поддерживает только zod 3.
- **Последствия.** Добавление разрешения — изменение каталога в `@iot/shared` и перезапуск API. Порядок выдачи конфиденциальных разрешений и параметры политики входа ждут ответа заказчика (open-questions, вопросы 5, 6, 8); механизм уже есть. Модель прав описана в `docs/architecture/access-model.md`.

## ADR-010. Справочники, студенты и защита форм от повторной отправки

- **Контекст.** Этап 04: учебные группы, дисциплины, закрепление преподавателей, база студентов (FR-006–FR-011), область данных преподавателя (FR-002), целостность при повторной отправке форм (NFR-006). Навигация зафиксирована (огр. 7), отдельного пункта «Группы» в ней нет.
- **Решение.**
  - Учебные группы и закрепление преподавателей размещены вкладками в служебном разделе «Дисциплины» (видны по разрешениям `groups.manage` и `disciplines.manage`); преподаватель видит в разделе только свои дисциплины и группы. Меню не меняется.
  - Студентов добавляет, импортирует, переводит и архивирует преподаватель (`students.manage`) только в пределах своих групп. Администратор не имеет разрешения `students.read`: группы и закрепления он ведёт, но списков студентов и их показателей не видит; учётные записи студентов он может только блокировать и сбрасывать им пароль в «Администрировании».
  - Студент создаётся вместе с учётной записью (роль «Студент», временный пароль, смена при первом входе) и записью о группе в `enrollments`. Код участника, если не указан, формируется автоматически (`S-` и 6 символов без похожих букв); логин по умолчанию — код в нижнем регистре, поэтому в логине нет ФИО.
  - Перевод закрывает текущую запись `enrollments` датой и открывает новую с причиной; архивирование скрывает студента из рабочих списков и закрывает вход, ничего не удаляя. Группу и дисциплину можно архивировать только без действующих студентов и закреплений.
  - Импорт выполняется в два шага: предпросмотр (`POST /api/students/import/preview`, файл CSV или XLSX до 2 МБ и 300 строк, тип проверяется по содержимому; CSV в UTF-8 или Windows-1251, разделитель «;», «,» или табуляция) и подтверждение корректных строк (`POST /api/students/import`), при котором все строки проверяются заново и создаются в одной транзакции. Формат колонок принят по умолчанию до ответа заказчика (open-questions, вопрос 7).
  - Формы, создающие записи, передают заголовок `Idempotency-Key`. Первый запрос сохраняет ответ в `idempotency_keys` (срок 24 часа), повтор с тем же ключом и теми же данными возвращает сохранённый ответ без новых записей, с другими данными — 409. Временные пароли в сохранённый ответ не попадают: при повторе вместо пароля возвращается `null`, новый пароль выдаётся в карточке студента.
  - Выбор группы и дисциплины в шапке — общий рабочий контекст (`apps/web/src/stores/context.ts`): списки содержат только доступные пользователю значения, раздел «Студенты» фильтрует по ним.
- **Последствия.** Показатели карточки студента, которых ещё нет (прогресс, успеваемость, выполненные задания, последняя активность), API возвращает как `null`, интерфейс показывает «Нет данных»; они заполнятся на этапах 09–13. Фильтр по профилю пока учитывает любой подтверждённый профиль — «текущий профиль» уточняется на этапе 09.

## ADR-011. Профиль студента, педагогические наблюдения и история

- **Контекст.** Этап 05: единая карточка студента с семью вкладками (п. 4.3, 6.3 ТЗ), педагогические наблюдения с датой и автором (FR-014), разделение видимости служебных заметок (FR-016), «Мой профиль» студента (п. 2.3). Навигация зафиксирована (огр. 7).
- **Решение.**
  - Профиль — вложенная страница раздела «Студенты» (`/students/:id`), а не новый пункт меню. Имя студента в списке ведёт в профиль; действия с карточкой (изменение ФИО, перевод, архив, новый пароль) открываются кнопкой «Управление карточкой» в прежнем диалоге.
  - Наблюдения добавляет преподаватель с отдельным разрешением `observations.manage` в пределах своей области данных. По умолчанию наблюдение служебное (`INTERNAL`); открыть его студенту (`STUDENT_VISIBLE`) — явный выбор автора. Изменять наблюдение может только автор; удаление не предусмотрено, чтобы история наблюдений сохранялась. Служебные наблюдения видят все преподаватели, которым доступен студент.
  - Наблюдения размещены на вкладке «Сопровождение» (п. 4.3: «рекомендации, комментарии»); кнопка «Добавить наблюдение» есть и в верхней карточке, как в макете.
  - Вкладка «История» строится из журнала аудита: события по студенту и его наблюдениям из закрытого списка значимых действий (`STUDENT_HISTORY_LABELS` в `@iot/shared`). Отдельная таблица событий не нужна: каждое изменение уже пишется в `audit_logs` в той же транзакции. Модули следующих этапов добавляют свои действия в этот список.
  - Студент получает собственные данные через `/api/cabinet/profile`: студент определяется по учётной записи из сессии, наблюдения отбираются по видимости на сервере. Студент может менять только поле «Интересы».
  - Текст наблюдения в журнал аудита не пишется: журнал читает администратор, которому содержание педагогических заметок не нужно по должности (п. 2.1).
- **Последствия.** Вкладки «Диагностика», «Мотивационный профиль», «Моя ИОТ», «Задания» и блок консультаций показывают пояснение, пока их не наполнят этапы 07–15. Кнопка «Создать ИОТ» из макета появится в верхней карточке на этапе 11.

## ADR-012. Конструктор методик: документ версии, неизменяемость и правила расчёта

- **Контекст.** Этап 06: настраиваемые методики с версиями (п. 4.4 ТЗ; FR-017, FR-020, FR-021, FR-026), контрольные примеры (п. 11.3), демо-методика до передачи реальных (огр. 1, ADR-003). Схема таблиц методик создана на этапе 01.
- **Решение.**
  - Содержимое версии (паспорт, вопросы, варианты, шкалы, ключи, правила интерпретации) передаётся одним документом `QuestionnaireContent` (`@iot/shared`). Черновик сохраняется целиком (`PUT /api/questionnaires/:id/versions/:versionId`): вопросы и шкалы черновика заменяются, ключи элементов документа сопоставляются с новыми id. Так конструктор не синхронизирует десятки мелких изменений, а ссылочная целостность (ключ указывает на вопрос и вариант этого же документа) проверяется в одном месте (`structuralIssues`).
  - Опубликованная версия неизменяема. Сервис отклоняет изменение (409), а триггеры БД `questionnaire_version_guard` и `questionnaire_content_guard` запрещают менять паспорт, вопросы, варианты, шкалы, ключи и правила опубликованной версии и удалять её — в том числе при гонке «сохранение во время публикации» и при обращении к БД в обход API. Разрешена только смена статуса.
  - Изменение — новая версия: черновик-копия действующей версии (не больше одного черновика у методики). Публикация новой версии переводит прежнюю в статус «Выведена из использования»: назначать её нельзя (этап 07), а её результаты остаются привязанными к ней и не пересчитываются. Процедура явного пересчёта (ревизия `RECALCULATION`, FR-026) не реализована: она нужна только по решению исследователя и будет оформлена отдельно.
  - Перед публикацией выполняется полная проверка (`publishIssues`): текст вопросов, не меньше двух вариантов у вопросов с выбором, целые границы шкалы Лайкерта (2–11 делений), ключи хотя бы у каждой шкалы, нет ключей на текстовые ответы, обратное кодирование только при известных минимуме и максимуме, непересекающиеся диапазоны уровней. Замечания возвращаются как ошибки полей (`questions.2.text` и т. п.).
  - Правила расчёта (`scoreQuestionnaire`): ключ без варианта даёт значение ответа (число, значение выбранного варианта, сумма значений выбранных вариантов), обратный ключ — `min + max − значение`; ключ по варианту даёт баллы (или значение варианта), если вариант выбран; вклад умножается на вес. Балл округляется до трёх знаков (как `DECIMAL(10, 3)`). **Если хотя бы на один вопрос шкалы нет ответа, балл шкалы не рассчитывается** (`null`, «Нет данных»), число пропусков сохраняется: частичная сумма занижала бы уровень (п. 1.8 CLAUDE.md, FR-074). Если реальной методике заказчика нужна иная обработка пропусков, правило добавляется как свойство шкалы после передачи методики. Диапазоны уровней — с включёнными границами; балл вне всех диапазонов остаётся без уровня.
  - Движок и проверки — чистые функции в `@iot/shared`: один и тот же код считает в предпросмотре конструктора, на сервере (этап 07) и в тесте контрольных примеров.
  - Контрольные примеры (п. 11.3): определение методики хранится в `apps/api/prisma/questionnaires/<методика>/v<N>.json` (из него сид заполняет БД), примеры — в `apps/api/test/fixtures/diagnostics/<методика>/<N>/*.json` (ответы и ожидаемые баллы и уровни по кодам шкал). Тест `control-examples.spec.ts` прогоняет все примеры и требует хотя бы один пример для каждого определения.
  - Демо-методика (`demo-motivation`, признак `is_demo`) обязана содержать «ДЕМО — не для исследования» в названии и источнике — иначе версия не публикуется. Копия демо-методики остаётся демо-методикой.
  - Диагностические направления п. 4.4 заполняются миграцией (нужны в любом окружении); их можно переименовывать и дополнять в разделе «Диагностика».
  - Методики — общий справочник: доступны всем пользователям с `diagnostics.manage` без ограничения областью данных. Администратор и исследователь методики не редактируют (п. 2.1).
- **Последствия.** Сохранение черновика меняет id его вопросов и шкал; на черновик ничего не ссылается (прохождения и назначения — только на опубликованные версии), поэтому это безопасно. Интерфейс после сохранения заменяет документ ответом сервера.

## ADR-013. Проведение диагностики: назначение, прохождение, ревизии результатов

- **Контекст.** Этап 07: назначение методики студенту или группе на период (FR-018, FR-019), прохождение с инструкцией, черновиком и проверкой полноты (UC-01), расчёт по утверждённым ключам (FR-020), сохранение даты, версии, ответов, баллов и времени прохождения (FR-023), ручной ввод бумажного бланка (FR-022), неизменяемость ответов и процедура исправления (FR-013). Таблицы `diagnostic_assignments`, `diagnostic_sessions`, `diagnostic_revisions`, `diagnostic_answers`, `diagnostic_scores` созданы на этапе 01.
- **Решение.**
  - Назначается только действующая (опубликованная) версия неархивной методики. Версия фиксируется в назначении и в каждом прохождении: публикация новой версии не меняет уже назначенные прохождения (FR-026, принцип 7).
  - При назначении группе прохождения создаются сразу для всех неархивных студентов группы; студентам пишется внутрисистемное уведомление (`notifications`, тип `diagnostic.assigned`). Показ уведомлений в шапке — этап 15 (FR-065). Назначать можно только группы и студентов из своей области данных (FR-002).
  - Период — `startsAt` включительно, `endsAt` не включительно; интерфейс задаёт даты, конец периода — начало дня после даты окончания. Незавершённые прохождения с истёкшим сроком получают статус «Срок истёк» при обращении к спискам (без фоновой задачи; планировщик появится на этапе 14).
  - Студент получает форму методики без значений вариантов, ключей и правил интерпретации (`DiagnosticForm`), а после завершения — только тексты интерпретации для студента (FR-016), без баллов. Черновик ответов хранится в `diagnostic_sessions.draft_answers`, только если методика допускает черновик; при завершении черновик удаляется.
  - Завершение — одна транзакция: проверка полноты (`answersIssues`, обязательные вопросы), сохранение исходных ответов без пропусков, расчёт `scoreQuestionnaire` по ключам версии прохождения, ревизия 1 (`INITIAL`) и время прохождения от нажатия «Начать». Повтор с тем же ключом `Idempotency-Key` возвращает прежний ответ (NFR-006).
  - Бумажный бланк вводит преподаватель: те же проверки и расчёт, источник `PAPER`, дата заполнения бланка, без времени прохождения. Ввод возможен и после окончания срока — бланки собирают позже.
  - Исправление ошибочного ввода — новая ревизия `CORRECTION` с полным набором ответов и обязательной причиной; расчёт по той же версии методики. Прежние ответы и баллы остаются; действующей считается ревизия `current_revision`. Причина пишется в журнал аудита, содержание ответов — нет (п. 2.1). Требует `diagnostics.manage` и `diagnostics.answers.read`.
  - Завершённое прохождение защищено триггером `diagnostic_session_guard`: меняется только номер действующей ревизии (и только вверх), удалить нельзя. Ответы, баллы и ревизии неизменяемы с этапа 01.
  - Исходные ответы и ревизии (`GET /api/diagnostic-sessions/:id/answers`) доступны только с `diagnostics.answers.read`; у администратора этого разрешения нет. Баллы по шкалам видит преподаватель с доступом к студенту во вкладке «Диагностика» профиля.
  - Прохождение — вложенная страница кабинета `/student/diagnostics/:id`; меню не меняется (огр. 7). Вопрос методики отображает общий компонент `QuestionField` — в предпросмотре конструктора, при прохождении и при вводе бланка.
- **Последствия.** Тип замера пока всегда «Первичный»: повторные замеры и сравнение — этап 08. Процедура пересчёта по новой версии ключей (`RECALCULATION`) по-прежнему не реализована (open-questions, вопрос 14).

## ADR-014. Повторная диагностика, сравнение замеров и обезличенная выгрузка

- **Контекст.** Этап 08: тип замера (первичный, промежуточный, повторный), назначение повторного замера той же или сопоставимой версии методики, сопоставимость которой фиксирует исследователь (UC-06), сравнение замеров (FR-024) с динамикой в профиле (FR-015), обезличенная выгрузка (FR-025), пропуски без нулей (FR-074). Поле `measurement_type` в назначениях и прохождениях и таблица `questionnaire_version_comparabilities` созданы на этапе 01.
- **Решение.**
  - Тип замера задаётся при назначении и копируется в каждое прохождение. Первичный замер проводится только по действующей версии. Для промежуточного и повторного можно выбрать любую опубликованную ранее версию методики (`PUBLISHED` или `RETIRED`), чтобы повторить замер той же версией после выхода новой. Черновик назначить нельзя.
  - Сопоставимость двух версий утверждает исследователь (новое разрешение `research.manage` роли «Исследователь»). Пара хранится упорядоченной (A — более ранняя версия), повтор отклоняется уникальным ограничением (409). Утверждение и отзыв (с причиной) пишутся в аудит. Сопоставимость не транзитивна: каждая пара утверждается явно.
  - Сравнение строится по каждой методике отдельно чистой функцией `buildDiagnosticComparisons` (`packages/shared/src/diagnostic-results.ts`). Базовый замер — самый ранний первичный, а при его отсутствии — самый ранний завершённый. В сравнение входят замеры не раньше базового той же версии или версии, сопоставимой с версией базового; остальные показываются отдельно с причиной. Шкалы сравниваются по коду. Изменение — последний замер минус базовый; если в одном из них нет балла или замер один — «Нет данных», а не ноль.
  - Профиль показывает таблицу баллов по замерам (текстовая альтернатива) и линейный график Chart.js (vue-chartjs, зафиксирован в CLAUDE.md п. 2). Пропуск на графике — разрыв линии; серии различаются цветом из токенов `--iot-chart-*` и формой точек.
  - Выгрузка FR-025 — `GET /api/diagnostic-results/export` (CSV UTF-8 с BOM и разделителем «;» или XLSX), строка — завершённое прохождение действующей ревизии: код участника, группа, методика, версия, тип замера, способ, дата, время прохождения, по шкалам — балл, уровень, число пропусков. Нет балла — пустая ячейка. Текст, начинающийся с «=», «+», «-», «@», выгружается с апострофом (защита от формул). Выгрузка доступна с `research.export` по всем студентам, так как не содержит персональных данных (п. 2.4), и записывается в аудит.
  - Интерфейс исследователя размещён в существующем разделе «Аналитика» (меню не меняется, огр. 7): блоки «Выгрузка результатов диагностики» и «Сопоставимость версий методик» видны по разрешениям; остальная аналитика — этап 17.
- **Последствия.** Пересчёт прежних прохождений по новой версии ключей по-прежнему не выполняется (open-questions, вопрос 14): сравнение разных версий возможно только через явное утверждение сопоставимости. Связь замеров с исследовательскими проектами (`research_measurements`) и сравнение групп — этап 17.

## ADR-015. Мотивационные профили: предложение системы и решение преподавателя

- **Контекст.** Этап 09: предварительный профиль по утверждённым правилам интерпретации (FR-027), показатели-основания (FR-028), подтверждение или корректировка с причиной (FR-029), три карточки со стратегиями (FR-030), переход к ИОТ (FR-031), история (FR-032), отсутствие ограничений сложности (FR-033), статус «Требуется дополнительная диагностика» при недостатке данных (п. 4.5). Пороги уровней и минимальный объём данных заказчик пока не передал (open-questions, вопрос 3), тексты стратегий не утверждены (вопрос 11).
- **Решение.**
  - Профиль формирует преподаватель кнопкой в карточке студента (UC-02), а не система автоматически после диагностики. Берётся последнее завершённое прохождение каждой методики (действующая ревизия); в профиле участвуют шкалы, у правил интерпретации которых в конструкторе задан уровень профиля (`interpretation_rules.motivation_level`).
  - Правило предложения — чистая функция `proposeMotivationLevel` (`packages/shared/src/motivation-profiles.ts`): уровень, на который указало большинство шкал, если шкал с определённым уровнем не меньше настройки `profiles.minScales` (по умолчанию 1, раздел «Настройки»). Нет таких шкал, их меньше минимума или голоса разделились поровну — уровень не предлагается, статус «Требуется дополнительная диагностика», причина сохраняется в основаниях. Правило принято до ответа заказчика.
  - Уровень присваивает только преподаватель с `profiles.manage`: тот же уровень — «Подтверждён», другой — «Скорректирован» с обязательной причиной. Профилю без предложенного уровня уровень вручную не присваивается (409). Повторное формирование без новых данных не создаёт записи; повтор запроса защищён заголовком `Idempotency-Key`.
  - Текущий профиль — последняя запись профилирования, на неё указывает `students.current_motivation_profile_id` (миграция `20261018120000_current_motivation_profile`). По нему работают карточка студента и фильтр списка (FR-008: утверждённый уровень, «ожидает решения преподавателя», «требуется дополнительная диагностика»). Пока новое предложение ждёт решения, действующим считается последний утверждённый профиль (`lastDecided`) — на него опирается проектирование ИОТ.
  - Каждый переход пишется в неизменяемую таблицу `motivation_profile_history` и в журнал аудита (`motivation_profile.proposed`, `.needs_more_diagnostics`, `.confirmed`, `.corrected`); события попадают во вкладку «История».
  - Студент видит только пояснение, утверждённое преподавателем (`student_summary`, по умолчанию — тексты правил интерпретации для студента), без уровня, оснований и причины корректировки (FR-016).
  - Тексты стратегий хранятся в `system_settings` (ключ `profiles.strategies`), по умолчанию — формулировки п. 4.5 ТЗ; меняет пользователь с `settings.manage` в «Настройках».
  - Кнопка «Сформировать ИОТ» доступна при утверждённом профиле и до этапа 11 ведёт в раздел «Индивидуальные траектории».
- **Последствия.** Профиль не связан со сложностью заданий (FR-033): ни одна проверка не использует уровень для ограничений. После передачи реальных методик правило и минимум шкал уточняются без изменения схемы.

## ADR-016. Библиотека материалов и заданий, загрузка файлов

- **Контекст.** Этап 10: переиспользуемые материалы (раздел «Библиотека материалов») и задания (раздел «Задания»): карточка задания п. 4.7 без полей конкретного назначения, стандартные и настраиваемые типы, уровни сложности, критерии оценивания (FR-046), поиск по дисциплине, теме и уровню (FR-047), файлы, ссылки и инструкции (FR-049). Контроль загрузки файлов (п. 8.3). Схема таблиц создана на этапе 01, миграция не нужна.
- **Решение.**
  - Файл загружается отдельным запросом `POST /api/files` (multipart, поле `file`) и затем указывается по id в материале или задании. Проверки: расширение из белого списка `FILE_UPLOAD_EXTENSIONS` (PDF, документы Word и OpenDocument, таблицы, презентации, TXT, PNG, JPG), размер до 20 МБ (`FILE_UPLOAD_MAX_BYTES`), соответствие содержимого формату по сигнатуре (`apps/api/src/library/file-signature.ts`; для Office Open XML — внутренняя структура архива, для TXT — корректный UTF-8 без нулевых байтов). MIME-тип берётся из таблицы форматов, заголовку `Content-Type` клиента не доверяем. Собственная проверка вместо внешней библиотеки: формат фиксирован белым списком из 14 расширений.
  - Содержимое хранится в `FILE_STORAGE_DIR` (по умолчанию `storage/<NODE_ENV>`, отдельный каталог на окружение, NFR-010) под случайным UUID без расширения; исходное имя — только в БД, без пути и управляющих символов. Выдача — `GET /api/files/:id` всегда как вложение (`Content-Disposition: attachment`, имя в `filename*` UTF-8), поэтому загруженный документ не исполняется в браузере.
  - Антивирусная проверка — вне MVP: в `FilesService` оставлена точка подключения `scan()`.
  - Область библиотеки: преподаватель видит и изменяет материалы и задания дисциплин из своих закреплений, а также общие материалы без дисциплины. Библиотека общая для преподавателей одной дисциплины (переиспользование), правок «только автором» нет; каждое изменение пишется в журнал аудита. Чужое — 404. Новую запись можно привязать только к своей дисциплине; новый файл — только загруженный самим пользователем (чужой файл по id прикрепить нельзя).
  - Ссылки принимаются только со схемами `http` и `https` (`SAFE_URL_PATTERN`), открываются с `rel="noopener noreferrer"`. Текст материала и инструкция — простой текст, разметка не исполняется.
  - Стандартные типы заданий п. 4.7 — каталог `SYSTEM_ASSIGNMENT_TYPES` в `packages/shared`, который API синхронизирует в `assignment_types` при запуске и в сиде (как каталог ролей): SQL-миграция дала бы идентификаторы UUID v4, а API принимает только UUID v7. Свои типы добавляет любой пользователь с `library.manage`.
  - Разрешение `library.manage` открывает и материалы, и задания библиотеки (описание разрешения — «Библиотека материалов и заданий»); `assignments.manage` остаётся для назначения и проверки (этапы 12, 13). Раздел «Задания» без `library.manage` показывает пояснение.
  - Изменение задания заменяет критерии и вложения целиком; если по критериям уже выставлены баллы, изменение критериев запрещено (409) — нужно новое задание. Архивирование не затрагивает уже назначенные задания и материалы этапов ИОТ.
  - Создание материала, задания и типа защищено `Idempotency-Key` (NFR-006). Повторная загрузка файла создаёт новую запись `files`, но не видимый дубль в библиотеке.
- **Последствия.** На этапе 13 сдача файлов использует тот же `FilesService` (проверки и хранение); правило доступа к файлу нужно будет расширить на попытки сдачи. Неиспользуемые загруженные файлы пока не удаляются — очистка вместе с резервным копированием (этап 21).

## ADR-017. Конструктор ИОТ: шаблоны, черновик, утверждение с версией

- **Контекст.** Этап 11 (UC-03, AT-05): создание ИОТ из шаблона или с нуля (FR-034), предложение шаблона по мотивационному профилю (FR-035), редактирование целей, сроков, этапов, заданий и способов сопровождения (FR-036), материалы этапов (FR-037), предпросмотр (FR-038), утверждение только преподавателем с правом (FR-039), несколько ИОТ по разным дисциплинам (FR-045), запрет ИОТ для контрольной группы исследования (огр. 4). Таблицы созданы на этапе 01, миграция не нужна.
- **Решение.**
  - Конечный автомат статусов `TRAJECTORY_TRANSITIONS` и проверка маршрута `trajectoryIssues` — в `packages/shared/src/trajectories.ts`; их применяют и сервер, и интерфейс. Режим `draft` проверяет только непротиворечивость (названия, порядок дат, сроки внутри маршрута и этапа, этапы не пересекаются); режим `approve` — ещё и полноту: цели, сроки маршрута, хотя бы один этап, цель и сроки каждого этапа, даты контрольных точек и сроки заданий.
  - Системные шаблоны — стандартный пятиэтапный (п. 4.6) и три варианта под уровни профиля — создаются каталогом `syncTrajectoryTemplates` при запуске API и в сиде (как типы заданий, ADR-016). Варианты содержат те же пять этапов и отличаются акцентом сопровождения из стратегии уровня (п. 4.5): содержание вариантов не выдумывается до ответа заказчика (open-questions, вопрос 16). Шаблон предлагается по последнему утверждённому профилю (`suggestTemplate`), иначе — стандартный. Это подсказка: преподаватель выбирает любой шаблон или маршрут с нуля.
  - При создании этапы шаблона копируются в `trajectory_stages`; способы сопровождения заполняются стратегией утверждённого профиля из «Настроек». По одной дисциплине у студента — не более одной действующей ИОТ (черновик, на утверждении, активная, требует корректировки), по разным — сколько угодно. Параллельное создание по той же паре сериализуется транзакционной блокировкой `pg_advisory_xact_lock`; повтор формы — `Idempotency-Key`.
  - Черновик сохраняется целиком (`PUT /api/trajectories/:id`): этапы, контрольные точки и задания с `id` изменяются, без `id` — создаются, отсутствующие — удаляются (черновик ещё не видел студент). Задания этапа — записи `trajectory_assignments` со статусом «Назначено» и сроком; студенту они показываются только у опубликованной ИОТ (этап 12). Материалы и задания — только из библиотеки дисциплины маршрута в области пользователя; архивные остаются, если уже были в этапе, но не добавляются заново.
  - Оптимистическая блокировка: сохранение, согласование, возврат, утверждение и архивирование передают метку `updatedAt` из последнего ответа; изменение применяется условием `updateMany … where updatedAt = метка и статус = ожидаемый`. Устаревшая форма получает 409 и не затирает чужие изменения; утверждается ровно та редакция, которую преподаватель видел в предпросмотре.
  - «На утверждении» — по желанию (open-questions, вопрос 10): отправить на согласование может преподаватель с `trajectories.manage`, утвердить или вернуть на доработку с причиной — с `trajectories.approve`. Утвердить можно и сразу из черновика.
  - Утверждение в одной транзакции: статус «Активна», `current_version + 1`, кто и когда утвердил, профиль на момент назначения (последний утверждённый), текущий этап — первый (статус «В работе»), время назначения заданий этапов, неизменяемый снимок версии в `trajectory_versions` (паспорт, этапы, контрольные точки, материалы, задания), уведомление студенту и запись в журнале аудита.
  - Огр. 4: студенту, который входит в контрольную группу действующего исследования (`research_participants.group = CONTROL`, проект в статусе «Подготовка» или «Проводится», не исключён), ИОТ не создаётся и не утверждается (403 с причиной); конструктор показывает причину заранее. Ведение участников — этап 17.
  - Область данных: ИОТ видна и изменяется преподавателем, который ведёт дисциплину маршрута в текущей группе студента (`trajectoryScopeWhere`); чужая — 404.
- **Последствия.** Этап 12 публикует активную ИОТ в кабинете и переиспользует карту этапов `StageMap.vue`. Этап 13 заменит «Нет данных» в проценте выполнения этапа на расчёт по заданиям. Этап 14 добавит корректировку активной ИОТ: изменение содержимого с новой версией и причиной, удалённые этапы архивируются (`archived_at`), а не удаляются.

## ADR-018. Кабинет студента: траектория и задания; назначение заданий

- **Контекст.** Этап 12 (AT-06): публикация утверждённой ИОТ в кабинете (FR-040), визуальная карта маршрута для преподавателя и студента (FR-041), назначение заданий студенту, нескольким студентам или группе (FR-048), выбор студентом из равнозначных заданий (FR-054); студент указывает интересы и предлагает изменения, но не меняет обязательные этапы (п. 2.3). Таблицы `trajectory_assignments`, `assignment_choice_groups`, `feedback` созданы на этапе 01, миграция не нужна.
- **Решение.**
  - Студент видит маршрут в статусах «Активна», «Требует корректировки», «Завершена» (`STUDENT_VISIBLE_TRAJECTORY_STATUSES`). Черновик и маршрут на согласовании не показываются, как и их задания: на этапе 11 задания этапа создаются в черновике со статусом «Назначено», поэтому видимость задания определяется статусом ИОТ (`publishedAssignmentWhere`, `cabinetAssignmentWhere` в `apps/api/src/library/library-scope.ts`). Отменённые и невыбранные назначения не действуют.
  - Кабинет отдаёт отдельный контракт `CabinetTrajectoryDto` без служебных полей (история версий и причины, метка редакции, код участника). Материалы этапа приходят с содержимым (текст, ссылка, файл), чтобы студент открывал их без доступа к библиотеке. Файлы студенту выдаёт `GET /api/cabinet/files/:id`: только материалы этапов своей утверждённой ИОТ и вложения своих действующих заданий; проверка — в `FilesService.readForStudent`, ответ всегда вложением.
  - Карта маршрута — тот же компонент `StageMap.vue` (обобщённый по типу этапа, со слотами «материал» и «задание»): студенту материалы открываются, задания ведут в карточку; у преподавателя — прежний вид. Во вкладке «Моя ИОТ» профиля — центральная карта действующей ИОТ (п. 6.3).
  - Назначение (FR-048) — `POST /api/student-assignments`: задания библиотеки одной дисциплины, студенты списком или вся группа; пользователь должен вести эту дисциплину в группе студента (FR-002). Каждый студент обрабатывается под транзакционной блокировкой `pg_advisory_xact_lock`: если хотя бы одно из заданий уже действует у студента, он пропускается с причиной, а не получает дубль; повтор формы — `Idempotency-Key` (NFR-006). Назначение вне маршрута не меняет утверждённую ИОТ: добавление задания в этап — корректировка маршрута с новой версией (этап 14).
  - Выбор из равнозначных (FR-054): набор `assignment_choice_groups` на каждого студента и варианты со статусом «Предложено на выбор». Студент выбирает ровно `required_count` вариантов один раз: выбранные становятся «Назначено», остальные — «Не выбрано»; повторный выбор — 409 (условное обновление `chosen_at IS NULL`). Наборы в ИОТ-конструкторе не добавлялись: это изменило бы содержимое и снимок версии маршрута.
  - Отмена — только не начатого задания вне ИОТ, с причиной; невыбранный набор отменяется целиком; задание этапа ИОТ — 409 (меняется корректировкой, этап 14).
  - Предложение изменить маршрут (п. 2.3) — запись `feedback` вида `ROUTE_CHANGE_PROPOSAL`, видимая студенту, с уведомлением преподавателю ИОТ. Маршрут, его версия и метка редакции не меняются; предложения не входят в снимок версии. Интересы студент по-прежнему указывает в «Мой профиль» (этап 05). Обсуждение и ответы на предложения — модуль обратной связи (этап 15).
  - Карточка студента текущей учётной записи для кабинета — общий метод `AccessScopeService.ownStudent` (раньше копии были в сервисах).
- **Последствия.** Этап 13 добавит сдачу и проверку заданий из карточки `/student/assignments/:id`, проценты выполнения этапов и просрочку. Этап 14 — корректировку ИОТ, в том числе изменение заданий этапа и разбор предложений студента. Этап 15 — ответы на предложения и консультации.

## ADR-019. Сдача и проверка заданий, учёт выполнения этапов

- **Контекст.** Этап 13 (UC-04, AT-07): приём ответов текстом, файлом или ссылкой (FR-050), повторная сдача после доработки (FR-051), оценивание по критериям (FR-052), сроки и статусы выполнения (FR-053), учёт выполнения этапа (FR-042) и статистика по этапу (FR-055). Таблицы `submissions`, `submission_files`, `assessments`, `assessment_criterion_scores`, `academic_results` созданы на этапе 01, миграция не нужна.
- **Решение.**
  - Правила — чистые функции в `packages/shared/src/submissions.ts`, их применяют и сервер, и интерфейс: `submissionIssues` (непустой ответ только в форматах задания; задание без форматов принимает любой), `checkAssessment` (принятое задание с критериями оценивается по каждому критерию от 0 до максимума, итог — сумма; без критериев балл не ставится; возврат требует комментария и идёт без баллов), `isAssignmentOverdue` (срок прошёл, а ответ не отправлен — «Назначено», «Выполняется», «Возвращено»), `assignmentProgress` и `nextStageStatus`.
  - Студент: `POST /api/cabinet/assignments/:id/start` («Приступить к выполнению», «Назначено» → «Выполняется»; необязательный шаг), `POST /api/cabinet/files` (загрузка файла ответа с теми же проверками, что в библиотеке), `POST /api/cabinet/assignments/:id/submissions` (`Idempotency-Key`). Сдача — условный переход статуса в «На проверке» и новая попытка с номером `attempt_number`; уже отправленный или выполненный ответ — 409. Прикрепить можно только файлы, загруженные самим студентом. Файлы своих ответов студент скачивает через `GET /api/cabinet/files/:id`.
  - Преподаватель: очередь `GET /api/student-assignments/review` (вкладка «На проверке» раздела «Задания»), карточка `GET /api/student-assignments/:id` и решение `POST /api/student-assignments/:id/assessments` (`Idempotency-Key`). Доступ — по парам группа×дисциплина области данных (`teacherAssignmentWhere`), чужое — 404. Проверяется только последняя попытка и только один раз (уникальность `assessments.submission_id`, условный переход статуса). Принятое задание с баллом записывается в `academic_results`; без балла запись не создаётся — фиктивных оценок нет (FR-005). Файлы ответа преподаватель скачивает через `GET /api/student-assignments/files/:fileId`, а не через библиотеку: для проверки нужно право на задания, а не на библиотеку.
  - Комментарий проверки и пояснения по критериям видны студенту — это обратная связь по заданию. Внутренние заметки преподавателя — модуль обратной связи (этап 15).
  - Учёт выполнения этапа: статус этапа пересчитывается при каждом изменении статуса его задания. Все действующие задания приняты — «Завершён» (`completed_at`); работа начата — «В работе»; назад статус не откатывается, этап без заданий не меняется. Если завершён текущий этап, текущим становится следующий незавершённый. Это ход выполнения, а не корректировка: версия и снимок ИОТ не меняются (FR-043), итоговое завершение маршрута — решение преподавателя (FR-044, этап 14).
  - Процент выполнения (этапа и маршрута) не хранится, а считается по статусам заданий: доля принятых среди действующих; без заданий — «Нет данных», а не 0 %. Отменённые, невыбранные и ещё не выбранные варианты не учитываются. В предпросмотре черновика выполнение не показывается.
  - Уведомления: преподавателю ИОТ (или назначившему вне маршрута) — о сдаче, студенту — о принятии или возврате. Журнал аудита: `assignment.submitted`, `assignment.accepted`, `assignment.returned` (номер попытки, балл); эти события попадают во вкладку «История» профиля. Содержимое ответов в журнал не пишется.
- **Последствия.** Мониторинг (этап 14) берёт прогресс и просрочку из тех же функций; там же — предупреждения о пропущенных контрольных точках и корректировка заданий этапа. Если этап без заданий должен завершаться, это решит преподаватель через корректировку или отметку контрольной точки (этап 14).

## ADR-020. Мониторинг, корректировка и завершение ИОТ

- **Контекст.** Этап 14 (UC-05, AT-08, AT-09): прогресс в процентах (FR-056), фильтры по студентам, дисциплинам, группам и периодам (FR-057), предупреждения о просрочках и пропущенных контрольных точках (FR-058), динамика (FR-059), отметка о дополнительном сопровождении (FR-060), переход к корректировке (FR-061), раздельный учёт учебной активности и диагностики (FR-062), корректировка с сохранением версии (FR-043) и завершение с итоговой оценкой (FR-044). Таблицы и поля (`trajectory_versions`, `trajectory_checkpoints.status`, `trajectories.final_assessment`, `students.support_status`) созданы на этапе 01 — миграция не нужна.
- **Решение.**
  - Мониторинг — модуль `apps/api/src/monitoring`: `GET /api/monitoring` (сводка, строки по ИОТ, предупреждения, динамика по неделям) и `GET /api/monitoring/trajectories/:id` (этапы с контрольными точками, оценки, динамика, версии). В мониторинг входят маршруты «Активна», «Требует корректировки» и «Завершена» студентов не в архиве; область — `trajectoryScopeWhere` (FR-002). Период ограничивает маршруты по пересечению сроков и события (оценки, отправленные ответы, обращения, диагностику) по датам; дни считаются по местному времени сервера колледжа. Не больше 500 строк за запрос, дальше — сузить фильтр.
  - Показатели п. 4.8: доля выполненных заданий и процент (`assignmentProgress`), завершённые этапы (выполнение образовательных целей), пройденные и пропущенные контрольные точки, средний результат оценённых заданий (`academic_results`, проценты от максимума), отправленные ответы (учебная активность), обращения за помощью (вопросы и сообщения о затруднениях `feedback`, запросы консультаций самим студентом — данные появятся на этапе 15), количество корректировок (версии после первой), завершённые диагностики. Пропуски — null и «Нет данных», не 0 (FR-005). Учебная активность и диагностика — отдельные показатели и отдельные блоки экрана (FR-062). Входы в систему не собираются и не учитываются (п. 4.8).
  - Пропущенная контрольная точка — `isCheckpointMissed` (`packages/shared/src/monitoring.ts`): отмечена «Пропущена» или дата прошла, а точка не пройдена. Фоновая задача `MonitoringAlertsService` (при запуске и раз в час, в окружении `test` не запускается сама) отмечает такие точки действующих ИОТ «Пропущена» и отправляет преподавателю маршрута по одному уведомлению на точку и на просроченное задание. Внешний планировщик не добавлялся: достаточно таймера в процессе API.
  - Контрольные точки отмечает преподаватель: `POST /api/trajectories/:id/checkpoints/:checkpointId/status` («Пройдена», «Пропущена», «Ожидается»). Это ход выполнения, версия не создаётся. Этап без заданий завершается, когда пройдены все его точки (`nextStageStatus`) — так решён долг этапа 13. Пересчёт этапов вынесен в `apps/api/src/trajectories/stage-progress.ts`: текущим становится первый незавершённый действующий этап.
  - Отметка о сопровождении (FR-060): `PUT /api/monitoring/students/:id/support-status` со статусом и обязательным основанием, в области преподавателя; аудит `student.support_status_changed`, событие в истории студента. Отдельное право не вводилось: отметку ставит тот, кто ведёт мониторинг студента (`students.read` + `monitoring.read`).
  - Корректировка (FR-043, UC-05): `POST /api/trajectories/:id/corrections` — полное содержимое маршрута, как при сохранении черновика, и причина. Новая версия становится действующей сразу, поэтому нужны `trajectories.manage` и `trajectories.approve` (FR-039: утверждает преподаватель с правом). Разрешена из «Активна» и «Требует корректировки», результат — «Активна», версия +1, снимок в `trajectory_versions` с причиной; прежние снимки не меняются. История выполнения сохраняется: убранный этап архивируется (`archived_at`), убранное задание отменяется; нельзя убрать начатое или выполненное задание, этап с такими заданиями и отмеченную контрольную точку, нельзя заменить задание в существующем назначении (400 с полями). Перенос даты пропущенной точки снова делает её ожидаемой; завершённый этап, в который добавлено задание, снова «В работе». Защита от повторной отправки — метка редакции `updatedAt` (повтор — 409, второй версии нет). Студент получает уведомление без текста причины; аудит `trajectory.corrected` (версии, число изменений, причина).
  - История версий: `GET /api/trajectories/:id/versions/:n` отдаёт снимок; отличия считает `trajectoryDiff` (паспорт, состав и порядок этапов, поля этапов, контрольные точки, задания и сроки, материалы; записи сопоставляются по id). Тот же расчёт показывает изменения на шаге «Предпросмотр» корректировки.
  - «Требует корректировки»: `POST /api/trajectories/:id/needs-correction` с причиной (из «Активна»). Завершение (FR-044): `POST /api/trajectories/:id/complete` с итоговой оценкой — только из «Активна»; при ответах на проверке — 409; незавершённые задания отменяются, выполненные остаются. Итоговая оценка видна студенту в «Моя траектория». Завершённую ИОТ можно перенести в архив (`archive`), из мониторинга она тогда уходит.
  - Интерфейс: раздел «Мониторинг» (`MonitoringView.vue`) и вложенная страница `/monitoring/:id` (`MonitoringDetailView.vue`) — пункт меню не добавлялся (огр. 7). Графики (`DynamicsCharts.vue`): количество принятых заданий и отправленных ответов — столбцы, средний результат — отдельная линия (без второй оси), неделя без оценок — разрыв; под графиками — таблица значений. Корректировка — режим `correction` конструктора `TrajectoryEditor.vue`: изменения не сохраняются по шагам, а подтверждаются одной версией с причиной; из мониторинга открывается ссылкой `/trajectories/:id?correct=1`.
- **Последствия.** Консультации, вопросы и сообщения о затруднениях (этап 15) сразу попадут в «обращения за помощью». Главная панель (этап 16) может брать сводку из `GET /api/monitoring`. Уведомления пишутся в `notifications`, бейдж в шапке — этап 15.

## ADR-021. Обратная связь, консультации, рефлексия и уведомления

- **Контекст.** Этап 15 (п. 4.9, FR-063–FR-068): сообщения преподавателя (рекомендации, комментарии к заданиям, краткосрочные цели, запрос самооценки), обращения студента (вопрос, сообщение о затруднении, запрос консультации, рефлексия, предложение изменить маршрут), консультации, разделение видимых студенту комментариев и внутренних заметок, уведомления с бейджем в шапке. Таблицы `feedback`, `consultations`, `reflections`, `notifications` созданы на этапе 01 — миграция не нужна.
- **Решение.**
  - Модуль `apps/api/src/feedback`: сообщения и рефлексия — `FeedbackService`, консультации — `ConsultationsService`, общие выборки и проверка привязки — `feedback-refs.ts`. Модуль `apps/api/src/notifications`: список и счётчик своих уведомлений, отметка о прочтении и общий способ записи уведомлений (`NotificationsService.notify`, `teachersFor`).
  - Сообщение — ветка: корневая запись `feedback` и ответы (`parent_id`). Привязка (FR-064) — к студенту, ИОТ, этапу или назначению задания; уточняется сверху вниз (задание задаёт этап и ИОТ, этап — ИОТ). Привязать можно только утверждённый маршрут, который видит студент («Активна», «Требует корректировки», «Завершена»): черновик ещё переписывается целиком и удаляет свои этапы и задания.
  - Внутренняя заметка (FR-068) — запись с видимостью `INTERNAL`. Внутренними бывают рекомендация и комментарий; цель и запрос самооценки адресованы студенту. Ответ в ветке внутренней заметки всегда внутренний; в открытой ветке преподаватель может ответить внутренней заметкой. Кабинет студента фильтрует записи и ответы по видимости в запросе к базе; у консультации студенту не передаётся поле `internalNote` (`withoutInternalNote`). Права на ветку — область данных студента (группы преподавателя), как у педагогических наблюдений (этап 05).
  - Обращение студента (вопрос, затруднение, предложение изменить маршрут) преподаватель отмечает рассмотренным (`resolved_at`); нерассмотренные затруднения дают фильтр «есть затруднения» в списке студентов (FR-008, реализован на этапе 04). Ответ на запрос самооценки — рефлексия с `requestId`: запрос закрывается.
  - Рефлексия (FR-066) — отдельная форма: самооценка 1–5 и три вопроса («что получилось», «что было трудно», «что дальше»), хотя бы одно поле. После контрольной точки — когда преподаватель отметил её «Пройдена» или «Пропущена»; одна рефлексия на точку (повтор — 409, повтор формы с тем же ключом — тот же ответ). При отметке точки студент получает уведомление «Заполните рефлексию». Точку с рефлексией нельзя удалить при корректировке маршрута (400) — так закрыт риск нарушения внешнего ключа из журнала этапа 14.
  - Консультации (FR-067): запрос студента → назначение времени (или сразу назначение преподавателем, в том числе из мониторинга — шаг UC-05) → проведена (итог для студента и внутренняя заметка) или отменена с причиной. Перенос назначенной — тем же действием «назначить время». Дата в прошлом — 400. История консультаций — вкладка «Сопровождение» профиля и вкладка «Консультации» раздела.
  - История взаимодействия (FR-063) — `interactionTimeline` в `packages/shared/src/feedback.ts`: сообщения, консультации и рефлексия одной лентой, новые сверху. Значимые действия пишутся в аудит и видны во вкладке «История»: `feedback.resolved`, `consultation.requested|scheduled|held|cancelled` (отмена — с причиной), `reflection.created`. Тексты сообщений, итогов и заметок в журнал не попадают: журнал читает администратор (п. 2.1).
  - Уведомления (FR-065): запись в `notifications` в той же транзакции, что и действие. Студенту — о видимом сообщении и ответе преподавателя, о рассмотрении обращения, о назначении, проведении и отмене консультации, о просьбе заполнить рефлексию; преподавателю — о вопросе, затруднении, ответе студента, запросе консультации, рефлексии. Адресат обращения студента — преподаватель ИОТ, а без привязки к ИОТ — преподаватели действующих закреплений группы. Бейдж в шапке обновляется опросом раз в минуту и при открытии списка; SSE не потребовался, e-mail и push — вне MVP (CLAUDE.md, п. 2).
  - Интерфейс: раздел «Обратная связь» преподавателя (`FeedbackView.vue`: вкладки «Обращения студентов», «Консультации», «Сообщения студентам»), вкладка «Сопровождение» профиля (`StudentSupportTab.vue`: лента, «Написать студенту», «Назначить консультацию»), блок «Комментарии к заданию» на странице проверки и «Вопросы и комментарии» на странице задания студента (`AssignmentComments.vue`), кнопка «Назначить консультацию» в мониторинге ИОТ, раздел «Обратная связь» студента (`MyFeedbackView.vue`). Пункты меню не менялись (огр. 7). Время консультации вводится полем «чч:мм» рядом с датой «дд/мм/гггг».
- **Последствия.** Обращения и консультации студента уже учитываются мониторингом как «обращения за помощью» (ADR-020). Главная панель (этап 16) может показывать нерассмотренные обращения и ближайшие консультации из `GET /api/feedback?open=true` и `GET /api/consultations?status=SCHEDULED`.

## ADR-022. Главная панель преподавателя и главная студента

- **Контекст.** Этап 16 (п. 4.1, 6.2, 6.5; FR-001–FR-005): шесть показателей, две диаграммы, последние задания, активность и предстоящие контрольные точки у преподавателя; четыре вопроса п. 6.5 у студента; раздел «Мои достижения». Новые таблицы не нужны — всё считается из существующих данных.
- **Решение.**
  - Один эндпоинт `GET /api/dashboard` (модуль `apps/api/src/dashboard`) вместо набора запросов из браузера: один ответ проще проверить на совпадение с данными (e2e) и с отфильтрованными списками. Сервис не дублирует правила, а берёт их у владельцев: показатели ИОТ (активные, средний %, просроченные) — `MonitoringService.overview` с тем же периодом; распределение профилей и число студентов — `MotivationProfilesService.distribution`; ожидающие проверки — общее условие `reviewQueueWhere` очереди проверки; «требуют внимания» — общее правило `NEEDS_ATTENTION` списка студентов (отметка о сопровождении FR-060 или нерассмотренное сообщение о затруднении). Поэтому карточка и список, куда она ведёт, всегда показывают одно число (FR-003).
  - Переход по карточке (FR-003): «Студентов» и «Требуют внимания» → «Студенты» (новый фильтр `needsAttention`, `?attention=1`); «Активных ИОТ», «Средний %», «Просроченных» → «Мониторинг» с периодом панели и статусом (новый фильтр `status` мониторинга, параметры читаются из адреса); «На проверке» → очередь проверки; легенда профилей → «Студенты» с фильтром профиля. Пункты меню не менялись (огр. 7).
  - Период (FR-004) — выбор на панели: учебный год (с 1 сентября, по умолчанию), последние 3 месяца, 4 недели, всё время (`dashboardPeriodRange` в `packages/shared/src/dashboard.ts`). Конец периода не ограничивается: будущие сроки нужны блоку предстоящих событий. Период ограничивает маршруты (по правилам мониторинга), назначенные задания и ленту активности; число студентов, очередь проверки и «требуют внимания» — текущее состояние. Группа и дисциплина — из шапки.
  - «Нет данных» (FR-005): показатель без базы — `null` (нет студентов → все карточки; нет маршрутов → ИОТ-показатели; средний % — как в мониторинге, без заданий `null`). Пустые диаграммы и списки заменяются пояснением с действием.
  - Диаграмма «Выполнение ИОТ» — столбцы по номеру этапа (1–5 в стандартном шаблоне): сколько маршрутов в работе («Активна», «Требует корректировки») завершили, ведут или не начали этот этап. «Мотивационные профили» — кольцевая диаграмма; легенда со ссылками — текстовая альтернатива. Цвета — токены `--iot-chart-*`; общий хелпер `apps/web/src/utils/chart.ts` (цвет токена для canvas, анимация с учётом `prefers-reduced-motion`) заменил копии в `DynamicsCharts.vue` и `DiagnosticComparison.vue`.
  - Блок «Предстоящие контрольные точки» дополнен назначенными консультациями (долг этапа 15), лента «Последняя активность» показывает нерассмотренные обращения студентов бейджем «Не рассмотрено». Состав блоков макета (экран 1) сохранён, изменено только название третьего списка.
  - Актуальность (FR-001): ответ не кэшируется; страница перечитывает данные раз в минуту, при возврате на вкладку и при смене контекста — тот же подход, что у уведомлений (ADR-021), без SSE.
  - Главная студента и «Мои достижения» собираются в браузере из существующих эндпоинтов кабинета (`/cabinet/trajectories`, `/cabinet/assignments`, `/cabinet/diagnostics`) чистыми функциями `studentGoals`, `studentTodos`, `studentAchievements`, `studentTeachers` (`packages/shared/src/dashboard.ts`): новых эндпоинтов и прав не нужно, сервер уже отдаёт только свои данные. Текущая цель — этап, отмеченный текущим, иначе первый незавершённый; прогресс — по заданиям этапа (нет заданий — «Нет данных»). «Где получить помощь» — преподаватели действующих маршрутов и кнопки вопроса и консультации (окно `StudentRequestDialog` этапа 15).
  - Пользователь без `students.read` и `monitoring.read` (администратор, исследователь) на главной видит ссылки на свои разделы вместо панели.
- **Последствия.** Мониторинг ограничивает выборку 500 маршрутами (ADR-020); при большем числе маршрутов в области показатели ИОТ панели считаются по первым 500 — для пилота (две группы по 20 студентов) запас достаточен. Отчёты (этап 18) могут переиспользовать те же правила показателей.

## ADR-023. Аналитика и исследовательский режим

- **Контекст.** Этап 17 (п. 2.4, 4.10; UC-07; FR-069–FR-075; огр. 4): семь видов аналитики, описательные статистики, сравнение групп, исследования с кодами участников, экспериментальной и контрольной группами, первичным и повторным замерами, обезличенная выгрузка. Таблицы `research_projects`, `research_participants`, `research_measurements` созданы на этапе 01 — миграции не нужно.
- **Решение.**
  - Описательные статистики — чистая функция `descriptiveStats` (`packages/shared/src/statistics.ts`): n, пропуски, среднее, медиана, выборочное SD (n − 1), минимум, квартили, максимум. Квартили — линейная интерполяция (тип 7 по Hyndman и Fan, как `QUARTILE.INC` в Excel и `quantile()` в R), чтобы исследователь получал те же числа, что во внешних пакетах. Пропуски не входят в расчёт и считаются отдельно; без значений все показатели `null` («Нет данных», FR-074). Точность — 0,001. Проверка — эталонные наборы в `statistics.spec.ts`. Критерии Манна — Уитни, Вилкоксона и Спирмена не реализованы (п. 10.2).
  - Аналитика преподавателя — один эндпоинт `GET /api/analytics` (модуль `apps/api/src/analytics`). Правила не дублируются: показатели ИОТ, успешность, активность и недельная динамика берутся из `MonitoringService.overview` (наблюдение — одна ИОТ), распределение профилей — из `MotivationProfilesService.distribution` (в целом и по каждой группе). Сравнение групп (FR-070) — `compareGroups`: строка «Все группы» и по строке на учебную группу. Результативность заданий — по назначениям библиотеки (назначено, сдано, принято, возвратов, результат принятых %). Динамика мотивации и сравнение до и после сопровождения — по выбранной версии методики и утверждённым сопоставимым с ней версиям (FR-072): от студента один первичный (самый ранний) и один повторный (самый поздний после первичного) замер; изменение — разность у студентов с обоими значениями. Незавершённые прохождения в расчёт не входят, их число показывается (FR-073). Период — те же пресеты, что на главной панели.
  - Исследования ведёт исследователь (`research.manage`; описание права расширено). Участники включаются целой учебной группой в ЭГ или КГ: исследователь не видит списков студентов, а AT-01 описывает именно группы. Код участника — `R001`… по порядку включения в исследование, внутри группы — в случайном порядке, чтобы код не повторял алфавитный список; код не связан с кодом участника карточки студента, поэтому данные разных исследований не сопоставляются по коду. Исключение участника сохраняет запись и код, но убирает его из расчётов. ФИО участников — только с индивидуальным разрешением `research.personal_data.read`; в выгрузку не попадает никогда.
  - Огр. 4 с двух сторон: этап 11 запрещает ИОТ участнику контрольной группы; этап 17 не включает в контрольную группу студента с маршрутом в работе («Черновик», «На утверждении», «Активна», «Требует корректировки») — 409 с кодами студентов (не ФИО).
  - Замер исследования фиксирует версию методики, тип замера и необязательный период. К замеру относится завершённое прохождение участника по этой версии и этому типу с датой завершения (местной) в периоде; из нескольких — самое раннее. Связь через назначения диагностики не используется: так в замер попадают и бумажные бланки (FR-022), а преподавателю не нужно отмечать исследование при назначении. Поле `diagnostic_assignments.research_measurement_id` остаётся на будущее.
  - Данные исследования (`buildResearchData`): по замерам, шкалам и группам ЭГ/КГ — описательные статистики; полное наблюдение — балл по каждой выбранной шкале в каждом выбранном замере; изменение между первым и последним выбранным замером методики считается только для одинаковых или утверждённых сопоставимыми версий, иначе — причина. Шкалы сравниваются по коду внутри методики.
  - Выгрузка (FR-071, FR-075): два набора — исходные данные (строка — участник: код, ЭГ/КГ, полнота наблюдения, по каждому замеру версия, дата и баллы) и сводные показатели (статистики и изменения); CSV (UTF-8 с BOM, «;») или XLSX. Запись таблиц вынесена в `apps/api/src/common/spreadsheet.ts` и общая с выгрузкой этапа 08. Каждая выгрузка пишется в аудит. Учебная группа в выгрузку исследования не входит: для анализа достаточно ЭГ/КГ, а сочетание кода и малой группы облегчает узнавание.
  - Интерфейс: в разделе «Аналитика» вкладки по правам — «Показатели» (преподаватель), «Исследования» и «Диагностика: выгрузка и сопоставимость» (исследователь); страница исследования `/analytics/research/:id` — вложенная, меню не менялось (огр. 7). Таблицы статистик — общий компонент `StatsTable.vue`; недельная динамика — графики мониторинга `DynamicsCharts.vue`.
- **Последствия.** Показатели ИОТ аналитики наследуют предел мониторинга 500 маршрутов (ADR-020). Интерпретация пропусков внутри методики (открытый вопрос 15) влияет на число полных наблюдений; до ответа заказчика шкала с пропуском — пропуск.

## ADR-024. Отчёты

- **Контекст.** Этап 18 (п. 4.10; FR-076–FR-080): индивидуальный отчёт студента, отчёты по группе, по реализации ИОТ и по диагностике; PDF и XLSX; в каждом отчёте дата формирования, период, показатели и автор.
- **Решение.**
  - Отчёт — документ `ReportDocument` (`packages/shared/src/reports.ts`): реквизиты, условия отбора и разделы с показателями, таблицей и пояснением. Сервис собирает документ, `report-renderer.ts` выводит его в PDF или XLSX, поэтому состав и подписи в форматах не расходятся. Модуль `apps/api/src/reports`.
  - Данные берутся у существующих сервисов: мониторинг (ИОТ), профили (профиль, распределение), сессии диагностики (результаты студента), аналитика (`AnalyticsService.motivationFor` для статистик шкал). Правила не дублируются, область данных (FR-002) наследуется: студент или группа вне области — 404.
  - PDF — `pdfmake` 0.2 с поставляемым Roboto (кириллица; сети и внешних шрифтов не нужно), альбомная A4, нижний колонтитул с номером страницы. XLSX — `exceljs`: лист «Сводка» с реквизитами и показателями и лист на каждую таблицу; пропуск в таблице — «Нет данных», текст с формулой экранируется.
  - Права: `reports.read` и `students.read` (как у аналитики). Исследователь отчётов по студентам не получает (п. 2.4): ему остаются обезличенные данные исследования. В отчёт не входят служебные заметки преподавателя (FR-016) и ответы диагностики. Администратор без `reports.read` отчётов не получает (п. 2).
  - Период — пресеты главной панели (`DashboardPeriod`), группа и дисциплина — из шапки. Каждое формирование пишется в аудит `report.generated` (вид, формат, период; без ФИО студентов в теле записи).
  - Интерфейс: раздел «Отчёты» (меню не менялось, огр. 7) — параметры (период, формат) и четыре карточки отчётов.
- **Последствия.** Отчёты по группе и по ИОТ наследуют предел мониторинга 500 маршрутов (ADR-020); при превышении в отчёте есть пояснение. Для отчёта по диагностике версия методики пока берётся по умолчанию (первая с прохождениями), параметр `versionId` API поддерживает, выбор в интерфейсе не добавлен.

## ADR-025. Безопасность и нефункциональные требования

- **Контекст.** Этап 19 (п. 8.3, NFR-001–NFR-006, AT-12): довести безопасность и нефункциональные требования до проверяемого состояния.
- **Решение.**
  - Права проверяются автотестами, а не списком вручную: обход всех маршрутов по метаданным (`route-guards.e2e-spec.ts`) и IDOR-обход с реальными идентификаторами чужих данных (`idor.e2e-spec.ts`). Новый маршрут без разрешения или без подстановки идентификатора роняет тест, поэтому решение о доступе принимается явно.
  - Заголовки безопасности — `helmet` (MIT) в `configureApp`, то есть одинаково в работе и в e2e-тестах. CSP строгая: API отдаёт JSON, файлы и страницу документации; встроенные стили разрешены ради swagger-ui. Политика для статики интерфейса задаётся в nginx (этап 21): PrimeVue вставляет стили во время работы, поэтому для интерфейса понадобится `style-src 'self' 'unsafe-inline'`.
  - `Cache-Control: no-store` для всех ответов API: в них персональные данные.
  - Предел JSON-тела — 2 МБ (крупная методика помещается). Ошибки разбора тела (`http-errors`) переводятся в их статус с понятным сообщением вместо 500.
  - XSS: данные выводятся только интерполяцией Vue; `v-html`, `document.write`, присваивание `innerHTML`/`outerHTML` из данных запрещены правилами ESLint. Санитайзер HTML не нужен: приложение не принимает и не показывает пользовательский HTML или Markdown.
  - Из ошибок Prisma в журнал не попадает текст сообщения (там аргументы запроса с ФИО и логинами), только класс, код и стек.
  - Просроченные ключи повторной отправки удаляются фоновой задачей (`IdempotencyCleanupService`), а не только при повторе того же ключа.
  - Нагрузка — k6 в Docker-образе (`grafana/k6:2.3.0`), без установки на машину. Сценарий открывает основные экраны 50 пользователями; порог — p95 ≤ 3 с на экран. Данные готовятся через API отдельным скриптом в отдельной базе.
  - Браузеры: проекты Playwright `firefox` и `webkit`. `pnpm test:e2e` запускает Chromium (десктоп и 360 px) и Firefox; WebKit — `pnpm test:e2e:webkit` в официальном образе Playwright, потому что на системах без пакетов Ubuntu он не запускается на хосте.
  - Ограничение числа одновременных генераций отчётов не вводится: на объёме пилота PDF по группе формируется за 0,2–0,6 с.
- **Последствия.** Добавлена зависимость `helmet` (apps/api). Проверка зависимостей — `pnpm audit:deps` (уровень high). Результаты — `docs/testing/security.md`, `docs/testing/load.md`.

## ADR-026. Развёртывание

- **Контекст.** Этап 21 (п. 8.1–8.3, NFR-007, NFR-008, NFR-010, AT-13, подготовка AT-14): установка на Linux-сервер колледжа, обновление без потери данных, резервное копирование с проверенным восстановлением.
- **Решение.**
  - Docker Compose (`docker-compose.prod.yml`; после ADR-027 — `docker-compose.standalone.yml`), пять сервисов: `postgres`, `api`, `web`, `nginx`, `backup`. База и API — во внутренней сети `backend` без выхода наружу; открыты только порты nginx.
  - Образы `api` и `web` многоступенчатые: сборка в `node:24-alpine`, в итоговом образе только production-зависимости (API) или статика (web, `nginxinc/nginx-unprivileged`). Оба работают не от root; `api`, `web`, `nginx` — без Linux-capabilities и с `no-new-privileges`.
  - Миграции применяются при старте контейнера API (`prisma migrate deploy`): применяет только новые миграции и никогда не сбрасывает базу. Для этого `prisma` перенесён в `dependencies` API — CLI нужен в рабочем образе.
  - Статика и прокси — два nginx: `web` отдаёт сборку и заголовки безопасности страниц (CSP `style-src 'self' 'unsafe-inline'` ради PrimeVue, см. ADR-025), внешний `nginx` — TLS, HSTS, gzip, лимит тела 25 МБ, маршрутизация `/api`. Адреса `api` и `web` nginx разрешает через DNS Docker с коротким TTL, чтобы пересоздание контейнера при обновлении не требовало перезапуска прокси.
  - Адрес клиента за прокси: переменная `TRUST_PROXY` (число доверенных прокси, по умолчанию 0) включает `trust proxy` в Express; в рабочем окружении — 1, nginx перезаписывает `X-Forwarded-For`. Без неё ограничение попыток входа считало бы всех пользователей одним адресом nginx. Значение по умолчанию 0: без прокси заголовок присылает клиент, и доверять ему нельзя.
  - Резервное копирование — отдельный контейнер на `postgres:16-alpine` (та же версия утилит, что у базы) с `crond`: `pg_dump -Fc` + архив тома файлов + контрольные суммы, запись через каталог `*.partial`, ротация по числу копий, права только root. Восстановление (`restore.sh`) проверяет суммы до изменений и отказывается работать при подключённых клиентах. Вне MVP: копирование на внешний носитель — средствами сисадмина колледжа.
  - Первая учётная запись на рабочем сервере — команда `node dist/cli/create-admin.js` (временный пароль, обязательная смена, запись в аудит). Демо-сид на рабочем сервере не запускается.
  - AT-13 — автотест `pnpm test:restore` на Node test runner: рабочая сборка отдельным проектом Compose, данные через API, копия → удаление стенда с томами → чистый стенд → восстановление → проверка входа, группы, файла побайтно и аудита.
- **Последствия.** Новых зависимостей нет (`prisma` перенесён из dev в production-зависимости API). После слияния нужен `pnpm install`. Документация — `docs/deploy/`, чек-лист AT-14 — `docs/acceptance/at-14-server.md`.

## ADR-027. Развёртывание через Coolify

- **Контекст.** Сервер колледжа обслуживается Coolify: код получается из GitHub по deploy key, обновление выполняется при пуше в `main`. Путь к файлу Compose в Coolify — `docker-compose.prod.yml`. Coolify не монтирует файлы репозитория в контейнеры (первый деплой с файлом ADR-026 упал на монтировании `docker/nginx/default.conf`) и отклоняет файл с переменными в путях томов. Сертификат для домена получает и HTTPS обслуживает администратор сервера своим прокси.
- **Решение.**
  - `docker-compose.prod.yml` — вариант для Coolify: внутренний `nginx` принимает HTTP на порту сервера из переменной `HTTP_PORT` (тот же номер внутри контейнера), на этот порт администратор направляет свой прокси с доменом и HTTPS. Конфигурация входит в образ (`docker/nginx/Dockerfile`, шаблон `docker/nginx/coolify.conf.template`), порт подставляется при старте (envsubst образа nginx). Порты ниже 1024 nginx занимает без root: Docker 20.10+ разрешает это внутри сетевого пространства контейнера.
  - Перед API два прокси (внешний и nginx), поэтому `TRUST_PROXY=2`; nginx дополняет `X-Forwarded-For` и передаёт `X-Forwarded-Proto` внешнего прокси.
  - Сервис `backup` временно исключён по решению администратора сервера; вернуть — из `docker-compose.standalone.yml` с абсолютным путём каталога копий.
  - Сети, имя проекта и имена томов задаёт Coolify; переменные — в интерфейсе Coolify.
  - Файл ADR-026 переименован в `docker-compose.standalone.yml` для сервера без Coolify; на нём остаются `scripts/deploy.sh` и тест восстановления AT-13 (`docker/test/restore.test.mts`).
- **Последствия.** Пока `backup` отключён, резервных копий по расписанию нет: копию перед обновлением с миграциями делают вручную (`pg_dump`), порядок — `docs/deploy/coolify.md`. Требование п. 8.3 о резервном копировании на рабочем сервере выполняется после возврата сервиса.

## ADR-028. Администратор ведёт базу студентов

- **Контекст.** Заказчик попросил, чтобы администратор видел всех студентов и мог их редактировать, не получая роль преподавателя и закрепления за группами. До этого у роли `admin` не было разрешений `students.read` и `students.manage`, и пункт «Студенты» был ему скрыт (вопрос 13 в `open-questions.md`).
- **Решение.**
  - Роль `admin` получает `students.read` и `students.manage`. Область данных администратора уже `all` (из-за `groups.manage`), поэтому он видит студентов всех групп: список, поиск, фильтры, профиль, добавление, импорт, изменение ФИО, перевод, архив, выдачу пароля.
  - Ответы на диагностические методики по-прежнему закрыты: `diagnostics.answers.read` администратору не выдаётся (п. 2.1 ТЗ). На вкладке «Диагностика» профиля он видит только методику, версию, даты, баллы и уровни шкал, как и любой сотрудник с доступом к студенту.
  - Разделы и вкладки, требующие преподавательских разрешений (ИОТ, задания, мотивационные профили — изменение, сопровождение, наблюдения — добавление), администратору по-прежнему недоступны; вкладки профиля показывают пояснение «Нет доступа».
  - Администратор видит педагогические наблюдения о студенте, включая служебные: они скрываются только от студента (FR-016).
- **Последствия.** Изменился только каталог прав в `packages/shared/src/auth.ts`; таблица `role_permissions` приводится к нему при запуске API (`syncRbacCatalog`), миграция БД не нужна. Пункт «Студенты» появляется у администратора после повторного входа.

## ADR-029. Способ расчёта шкалы: сумма или среднее

- **Контекст.** Движок считал балл шкалы только суммой вкладов ключей. Методика «Мотивация учебной деятельности» (А. А. Реан, В. А. Якунин, модификация Н. Ц. Бадмаевой), утверждённая для исследования, требует среднего показателя по каждой шкале; число пунктов в её шкалах — от 2 до 7, поэтому суммы шкал между собой не сопоставимы. Методика «Мотивация обучения» Т. Ильиной считается суммой взвешенных баллов. В рабочей базе обе методики уже заведены, по методике Ильиной есть прохождение.
- **Решение.**
  - У шкалы появилось поле «Способ расчёта» (`questionnaire_scales.aggregation`): `SUM` или `MEAN`. Среднее — сумма вкладов, делённая на число вопросов шкалы (несколько ключей на варианты одного вопроса — один пункт), с округлением до 0,1 по указанию заказчика.
  - Миграция задаёт существующим шкалам `SUM`; API без поля в запросе и файлы определений без поля тоже дают `SUM`. Прежние результаты не меняются.
  - Способ расчёта — часть правил обработки (FR-026): он меняется только в новой версии методики, старые прохождения не пересчитываются.
  - Сопоставимость версий, где одна шкала считается по-разному, сервер не утверждает: баллы в разных единицах.
- **Последствия.** Для методики Реана — Бадмаевой в рабочей базе нужно выпустить новую версию со способом «Среднее по пунктам» и пороги уровней в единицах среднего (1–5). Правила формирования мотивационного профиля по этим шкалам — этап 24.

## ADR-030. Правило мотивационного профиля по внутренним шкалам

- **Контекст.** До этапа 24 уровень профиля предлагался голосованием шкал (ADR-015): каждая шкала с заданным в правиле интерпретации «вкладом в профиль» указывала на уровень, побеждало большинство. Научный руководитель ВКР указал, что внешняя мотивация не должна повышать уровень, а результаты двух методик — сводиться по явному правилу. Заказчик 2026-10-23 утвердил рабочие нормы исследования: Реан — Якунин (модификация Бадмаевой) — среднее внутренних шкал (≥ 4,0 высокий, 3,0–3,9 средний, < 3,0 низкий); Ильина — процент от максимума внутренних шкал (≥ 67 % высокий, 34–66 % средний, < 34 % низкий); сведение: совпали — этот уровень, разница в одну ступень — более низкий, «высокий/низкий» — «Требуется дополнительная диагностика», одна методика — «Недостаточно данных».
- **Решение.**
  - У шкалы появилось поле «Роль в мотивационном профиле» (`questionnaire_scales.motivation_role`): `INTRINSIC`, `EXTRINSIC`, `REFERENCE`; по умолчанию `REFERENCE`. Роль — часть правил интерпретации (FR-026): меняется только новой версией.
  - Способ расчёта уровня методики выводится из способа расчёта шкал: если все внутренние и внешние шкалы — «Среднее по пунктам», уровень задаёт среднее внутренних шкал (до 0,1); иначе — процент суммы внутренних шкал от их максимума (до целого). Отдельной настройки методики не вводится: у Реана шкалы — средние (этап 23), у Ильиной — суммы. Пороги — константы `METHODOLOGY_LEVEL_THRESHOLDS` в `packages/shared/src/motivation-profiles.ts`: это утверждённые нормы исследования, а не настройка.
  - Округление перед сравнением с порогом: среднее — до 0,1 (как баллы шкал), процент — до целого (пороги заданы целыми числами без зазора между 66 и 67).
  - Максимум шкалы для процента считает `scaleScoreRange`; функция исправлена: ключи на разные варианты вопроса с одним ответом больше не складываются (раньше максимум у Ильиной завышался, что влияло только на подсказку конструктора).
  - Внешняя мотивация считается тем же способом; если она строго выше внутренней — предупреждение преподавателю (`extrinsicPrevails`), уровень не меняется.
  - «Недостаточно данных» и «высокий/низкий» дают существующий статус «Требуется дополнительная диагностика» (п. 4.5 ТЗ); вид итога различается полем `basis.outcome` и текстом причины. Новый статус профиля не вводится, чтобы не менять фильтры, отчёты и аналитику.
  - Новое правило действует, если у последнего прохождения хотя бы одной методики есть внутренняя шкала; методики без ролей шкал в нём не участвуют. Если ролей нет ни у одной пройденной методики, действует прежнее правило (демо-методика, старые версии в рабочей базе).
  - Сохранённые профили не пересчитываются; в `basis` нового правила записываются `rule`, `methodologies`, `outcome`, `explanation`.
- **Последствия.** В рабочей базе для методик Реана и Ильиной нужно выпустить новые версии с ролями шкал (какие шкалы внутренние и внешние, решает заказчик). Решение по уровню по-прежнему принимает преподаватель (FR-029). Открытый вопрос 3 закрыт этим решением.

## ADR-031. Занятия и журнал педагогических наблюдений

- **Контекст.** Для исследования ВКР нужны регулярные наблюдения за всеми студентами группы на занятиях по единым критериям, а не только произвольные заметки FR-014. Заказчик 2026-10-23 утвердил: занятия (дата, время, группа, дисциплина, преподаватель) вводятся вручную или импортом расписания `Дата | Время | Группа | Дисциплина | Преподаватель`; критерии — активность на занятии, включённость в работу, самостоятельность, инициативность, доведение задания до конца (список редактируется в «Настройках»); оценка 1–5, отметки «Не наблюдалось» и «Отсутствовал»; наблюдаются все студенты. Меню менять нельзя (огр. 7).
- **Решение.**
  - Новые таблицы: `lessons`, `observation_criteria`, `lesson_journal_entries` (студент на занятии, отметка «Отсутствовал»), `lesson_ratings` (оценка по критерию; `score = NULL` — «Не наблюдалось»). Отсутствие строки оценки — «нет данных», а не ноль (FR-074). Миграция аддитивная и добавляет пять критериев по умолчанию.
  - Время занятия хранится строкой «ЧЧ:ММ» местного времени вместе с датой (`DATE`): расписание не зависит от часового пояса сервера. Уникальность — группа, дисциплина, дата, время: повторная загрузка того же расписания пропускает существующие занятия.
  - Критерии — таблица, а не системная настройка: оценки ссылаются на критерий, переименование не ломает историю. Критерий не удаляется, а архивируется; архивный критерий не предлагается в новых журналах, но остаётся в журналах, где по нему уже есть оценки.
  - Размещение в интерфейсе без изменения меню: вкладка «Занятия» в служебном разделе «Дисциплины» (расписание — это пары «группа — дисциплина», раздел доступен и администратору, и преподавателю), страница журнала `/disciplines/lessons/:id`, история наблюдений — блок «Наблюдения на занятиях» на вкладке «Сопровождение» профиля студента, критерии — раздел «Настройки».
  - Права: новое разрешение `lessons.manage` (расписание) у администратора и преподавателя. Преподаватель добавляет, импортирует и удаляет занятия только по своим парам «группа — дисциплина» (FR-002); администратор — по всем группам и указывает преподавателя. Журнал заполняет только сотрудник с правом `observations.manage` (у администратора его нет). Студенту журнал не передаётся ни в одном маршруте (FR-016).
  - В журнале — все действующие студенты группы и студенты, уже отмеченные на этом занятии (переведённые или архивные не теряются). Журнал сохраняется целиком (`PUT`), частичное заполнение допустимо: статус «заполнен частично» и счётчик «отмечено N из M». Журнал будущего занятия не заполняется. Занятие с записями в журнале не удаляется.
  - Преподаватель в файле расписания сопоставляется по ФИО полностью, «Фамилия И. О.», «Фамилия И.» или по фамилии; неоднозначное совпадение — ошибка строки. Разбор CSV/XLSX вынесен в общий модуль `apps/api/src/common/table-import.ts` (им пользуется и импорт студентов, понадобится импорту оценок на этапе 26); ячейки-даты и время Excel преобразуются в текст «дд.мм.гггг» и «ЧЧ:ММ».
- **Последствия.** Средние оценки по критериям считаются только по оценкам 1–5. Показатели наблюдений «до/после» для ЭГ и КГ строятся на этих данных на этапе 27.

## ADR-032. Академическая успешность по семестрам

- **Контекст.** Для исследования ВКР нужна академическая успешность студентов по семестрам: оценки колледжа загружаются из файла `ФИО | Группа | Учебный год | Семестр | Дисциплина | Оценка 0–100`, исходные оценки хранятся, считаются средний балл по дисциплине и общий за семестр, сравниваются два семестра. Заказчик 2026-10-25 уточнил: по дисциплине за семестр бывает несколько текущих оценок; общий балл за семестр — среднее средних по дисциплинам; в профиле студента успеваемость показывается блоком на вкладке «Диагностика» (направление «академическая успешность», п. 4.4 ТЗ), набор вкладок п. 4.3 не меняется. Меню менять нельзя (огр. 7).
- **Решение.**
  - Оценки хранятся в существующей таблице `academic_results` (п. 7 ТЗ, «учебные достижения») с новым источником `SEMESTER_IMPORT` и новыми столбцами `period_id`, `group_id` (группа из файла), `import_id`; шкала 0–100 (`max_score = 100`). Новые таблицы: `academic_periods` (учебный год «гггг/гггг» и семестр 1 или 2, уникальная пара) и `grade_imports` (файл, автор, число оценок, отпечаток содержания, отметка об отмене). Миграция аддитивная: значение перечисления, столбцы с `NULL` и таблицы; ограничение `CHECK` требует для оценок за семестр периода, группы, загрузки и диапазона 0–100.
  - Модули оценок за задания (мониторинг, аналитика) отбирают строки через назначение задания, поэтому оценки за семестр в их показатели не попадают.
  - Расчёт — чистые функции в `packages/shared/src/grades.ts`: средний балл по дисциплине — среднее её оценок; общий балл — среднее неокруглённых средних по дисциплинам (каждая дисциплина весит одинаково); округление до 0,1. По группе: средний по дисциплине — среднее средних студентов, общий — среднее общих баллов студентов с оценками. Нет оценок — «нет данных» (`null`), разность семестров при пропуске не считается (FR-074).
  - Импорт по образцу импорта расписания (ADR-031): общий разбор CSV/XLSX, предпросмотр с ошибками по строкам, подтверждение с ключом идемпотентности, проверка заново и «всё или ничего». Студент ищется внутри группы из файла среди текущего состава и всех, кто в ней учился (`enrollments`): по ФИО полностью, «Фамилия Имя», «Фамилия И. О.» или «Фамилия И.»; одной фамилии недостаточно, неоднозначное совпадение — ошибка строки. Архивные группы и дисциплины сопоставляются (оценки прошлых семестров). Семестры создаются при первой загрузке.
  - Повторная загрузка: строки с одинаковыми оценками законны (несколько текущих оценок), поэтому дубли по строкам не ищутся. Защита от повторной загрузки того же файла — отпечаток SHA-256 содержания (студент, семестр, дисциплина, оценка; не зависит от порядка строк и формата файла): при действующей загрузке с тем же отпечатком предпросмотр предупреждает, импорт отклоняется (409).
  - Ошибочную загрузку отменяет её автор или администратор: оценки загрузки удаляются, запись о загрузке остаётся с отметкой об отмене; загрузка и отмена пишутся в журнал аудита (`grades.imported`, `grades.import_cancelled`).
  - Права: новое разрешение `grades.manage` у администратора (все группы) и преподавателя (только свои пары «группа — дисциплина», FR-002). Просмотр — с правом `students.read` в пределах доступных студентов и групп; студенту и исследователю оценки этим модулем не передаются (обезличенная выгрузка — этап 27).
  - Интерфейс без изменения меню: вкладка «Успеваемость» служебного раздела «Дисциплины» (группа, семестр, сравнение с другим семестром, импорт и список загрузок) и блок «Академическая успешность» на вкладке «Диагностика» профиля студента (оценки и средние по семестрам, сравнение двух семестров).
- **Последствия.** Средний балл за семестры 1 и 2 для широкой выгрузки ЭГ и КГ (этап 27) берётся из этих данных теми же функциями расчёта.

## ADR-033. Исследовательская аналитика ЭГ и КГ и широкая выгрузка

- **Контекст.** Этап 27: для исследования ВКР нужны показатели экспериментальной и контрольной групп по шкалам диагностики, среднему баллу за семестры (ADR-032) и педагогическим наблюдениям на занятиях (ADR-031) на первичном и повторном замерах, а также «широкая» обезличенная выгрузка — одна строка на участника — для внешнего расчёта критериев Манна — Уитни, Вилкоксона и Спирмена (сами критерии в приложение не входят, п. 10.2 ТЗ). Заказчик 2026-10-25 решил: семестры «до» и «после» выбирает исследователь в окне выгрузки (по умолчанию — два последних семестра с оценками участников); наблюдения «до» и «после» — два периода дат, по умолчанию граница — дата начала исследования; наблюдения выгружаются средней по всем критериям и по каждому критерию.
- **Решение.**
  - Новых таблиц и миграций нет: данные берутся из `research_participants`, `academic_results` (`source = SEMESTER_IMPORT`) и `lesson_ratings`/`lesson_journal_entries`/`lessons`.
  - Расчёт — чистая функция `buildResearchOutcomes` (`packages/shared/src/research.ts`). Средний балл за семестр — общий балл семестра `summarizeSemester` (как в разделе успеваемости). Наблюдения за период — средняя оценок 1–5 по каждому критерию и средняя по критериям (среднее неокруглённых средних, каждый критерий весит одинаково — по аналогии с общим баллом за семестр); «Не наблюдалось» и отсутствие не учитываются; округление до 0,1. По каждому показателю и группе ЭГ/КГ — описательные статистики «до», «после» и разности «после − до» у участников с обоими значениями (парные данные). Пропуск — пропуск, не ноль (FR-074); исключённые участники не учитываются.
  - API: `GET /api/research-projects/:id/data` дополнен параметрами `gradesBeforePeriodId`, `gradesAfterPeriodId`, `observationsBeforeFrom|To`, `observationsAfterFrom|To` и полем ответа `outcomes`. Если не указан ни один семестр — два последних семестра с оценками участников; если не указана ни одна граница периодов — «до» по день накануне начала исследования, «после» — с начала до окончания (без даты начала периоды не заданы). Одинаковые семестры, неизвестный семестр, перепутанные границы и пересечение периодов — 400 с указанием поля.
  - Выгрузка `GET /api/research-projects/:id/export` получила набор `wide` (`buildResearchWideTable`): код участника, группа ЭГ/КГ, баллы выбранных шкал по выбранным замерам с подписью «до» (первичный), «после» (повторный) или «промежуточный» (при нескольких замерах одного типа одной методики — с названием замера), средний балл за семестры и средние наблюдений «до» и «после». Методика и версия, семестр или период — в заголовке колонки. Ф. И. О., логины и учебная группа не выгружаются (FR-075). Сводные показатели (`aggregate`) дополнены строками «до», «после» и изменения по этим показателям. В аудит `research_data.exported` записываются выбранные семестры и периоды.
  - Доступ не меняется: данные и выгрузка — с правами `research.read` и `research.export`; исследователь видит только коды участников. Оценки и наблюдения отдаются ему только в обезличенном виде в составе данных исследования.
  - Интерфейс: поля выбора и таблицы — в существующем блоке «Данные исследования» страницы исследования; меню не меняется (огр. 7).
- **Последствия.** Для расчёта критериев исследователь выгружает широкую таблицу и обрабатывает её в статистическом пакете; при изменении правил расчёта среднего балла или наблюдений меняются и показатели исследования (функции общие).

## ADR-034. Демонстрационный режим с активностью за период исследования

- **Контекст.** Заказчик 2026-10-29 попросил в «Администрировании» скрытую панель, которая создаёт видимость полного использования системы: студенты групп ПО-9 ЭГ и ПО-9 КГ проходят существующие методики (первичный замер) и получают мотивационный профиль, ЭГ занимается по ИОТ (сначала математика и информатика; с этапа 28 — «ДО Веб-дизайн» и информатика; с версии 1.28.7 — только «ДО Веб-дизайн») с заданиями по уровню профиля, по каждому занятию (два в неделю) заполняется журнал наблюдений, создаётся исследование ЭГ/КГ с замерами, дисциплины первого курса и преподаватели, обращения, консультации, ответы, оценки за семестры; отдельной кнопкой — повторный замер после ИОТ. Период — октябрь 2025 — апрель 2026 года. В рабочей базе уже есть реальные студенты и методики, их нельзя портить. Переключение должно быть доступно в рабочем окружении, а на сайте не должно быть отметки о демо-режиме.
- **Решение.**
  - Демо-данные живут в отдельной базе `<имя рабочей базы>_demo` на том же сервере PostgreSQL. «Подготовить данные» пересоздаёт её миграциями Prisma, переносит туда рабочие данные (без журнала аудита и уведомлений; триггеры и внешние ключи на время переноса отключены) и запускает генератор. Рабочая база не изменяется.
  - Переключение: `PrismaService` направляет обращения к моделям в базу, выбранную `databaseRouter` (`apps/api/src/prisma/database-router.ts`). Пока демо-отображение включено, все запросы всех пользователей идут в копию; генератор пишет в копию через `AsyncLocalStorage` и при выключенном режиме. Признак режима хранится в рабочей базе (`system_settings`, ключ `demo.mode`) и восстанавливается после перезапуска API (с применением новых миграций к копии).
  - Генератор (`apps/api/src/demo/demo-activity.ts`) пишет данные с датами периода исследования. Ответы на методики подбираются так, чтобы правило профиля этапа 24 давало уровень, к которому тяготеет студент; баллы считаются тем же движком, предложение профиля — тем же `collectBasis`, решение принимает преподаватель. Уже пройденные в рабочей базе диагностики и профили переносятся в окно первичного замера. Прочие завершённые прохождения той же методики (прежние версии, например без ролей шкал, и повторные попытки) переносятся на дни раньше замера: профиль берёт последнее прохождение каждой методики, и им становится прохождение актуальной версии. Профилей «Требуется дополнительная диагностика» демо не оставляет: если уровни методик всё же расходятся или не определяются, ответы прохождений в копии заменяются сгенерированными, и студенту предлагается новый профиль; заменённый профиль рабочей базы остаётся в истории днём раньше. У студентов из списка `DEMO_FRESH_DIAGNOSTICS` (`apps/api/src/demo/demo-catalog.ts`, по просьбе пользователя — S-8JGXYQ) прохождения, профили и индивидуальные назначения диагностики рабочей базы в копии удаляются, и первичный замер проходится заново. В панели показывается версия системы — поле `version` корневого `package.json` (подставляется в веб при сборке, `apps/web/vite.config.ts`): `1.<номер последнего этапа>.<номер правки после него>`, при каждом выпуске увеличивается вручную. Повторный замер повышает внутреннюю мотивацию ЭГ на 0,15–0,3 склонности и почти не меняет КГ; повторный замер проходят все студенты обеих групп, поэтому парный анализ строится по полным парам.
  - С версии 1.28.7 (просьба пользователя 2026-10-30) учебная активность демо — только по «ДО Веб-дизайн» (`MAIN_DISCIPLINE`): занятия (два в неделю), задания, ИОТ ЭГ, оценки за семестры и контрольные работы. Задания — темы рабочей учебной программы 2023–2024 (повторяющиеся темы — одним заданием), цель задания — критерий оценивания темы: этапы ИОТ строятся по модулю СК01 «Разработка дизайна веб-приложений», задания модулей СК02 «Проектирование, разработка и оптимизация веб-приложений» и СК03 «Проектирование и разработка информационных систем» (с версии 1.28.8) — только в библиотеке. Контрольная группа занимается без ИОТ (огр. 4), но с версии 1.28.9 получает общие задания на группу, как при назначении из библиотеки (без маршрута): на каждом этапе — задание среднего уровня со сроком до конца этапа, со сдачей и проверкой. Прочие дисциплины первого курса добавляются только в справочник (показ расширения перечня): без преподавателей, заданий, материалов, занятий и оценок. Преподаватели не создаются (до 1.28.7 генератор создавал преподавателей дисциплин с паролем `teacher_kpvk123`); дисциплину ведёт преподаватель рабочей базы с логином `super_prepod` (если его нет — первый преподаватель). Преподаватели без роли администратора закрепляются за «ДО Веб-дизайн» в обеих группах, администратор с ролью преподавателя — тоже только за ней: доступ ко всем группам ему даёт роль.
  - Интерфейс: диалог «Демонстрационное отображение» открывается тройным щелчком по заголовку раздела «Администрирование»; меню и вкладки не меняются (огр. 7). API — `GET|DELETE /api/admin/demo`, `POST /api/admin/demo/prepare|repeat`, `PUT /api/admin/demo/mode`, право `users.manage`.
  - Создание и удаление базы и отключение триггеров требуют прав владельца сервера PostgreSQL — так настроены контейнер `postgres` и окружения разработки.
- **Последствия.** Всё, что пользователи делают при включённом демо-отображении, остаётся в копии и в рабочую базу не попадает; при переключении пользователь может быть разлогинен (сессии входа у баз разные). Демо-данные не являются результатами исследования, их нельзя использовать как реальные.

## ADR-035. Академические достижения: контрольные работы ЭГ и КГ

- **Контекст.** Этап 28 (решения заказчика 2026-10-29): гипотеза ВКР предполагает рост не только мотивации, но и успеваемости. Обе группы (ПО-9 ЭГ и ПО-9 КГ) учатся по программе дополнительного образования «Веб-дизайнер», поэтому успеваемость сравнивается по одинаковым входным и итоговым контрольным работам с единой рубрикой; текущие оценки за индивидуальные задания ИОТ между группами не сравниваются — задания разной сложности. Нужны ввод результатов по 100-балльной шкале, отдельный учёт отсутствия и невыполненной работы (не ноль), индивидуальная динамика, сравнение ЭГ и КГ и обезличенная выгрузка. Оценки за семестр (этап 26, ADR-032) уже есть — модуль расширяет их, а не дублирует.
- **Решение.**
  - Новый пункт меню преподавателя «Академические достижения» сразу после «Мониторинга» (заказчик явно согласовал изменение структуры меню, огр. 7). В разделе две вкладки: «Контрольные работы» и «Оценки за семестр» — последняя перенесена из раздела «Дисциплины» без изменений. Журнал наблюдений остаётся в «Дисциплинах».
  - Таблицы `control_works` (дисциплина, тема, вид контроля `ENTRY`/`CURRENT`/`FINAL`, критерии оценивания текстом), `control_work_groups` (группа и дата проведения в ней) и `control_results` (балл 0–100 с точностью 0,1 **или** отметка `ABSENT`/`NOT_SUBMITTED`/`EXEMPT`; ровно одно из двух — CHECK в базе). Нет строки — «нет данных». Миграция только добавляет объекты.
  - Одна работа назначается нескольким группам: одинаковое задание и рубрика у ЭГ и КГ. Критерии хранятся текстом, вводится итоговый балл (решение заказчика: без баллов по каждому критерию).
  - Ведомость группы — все студенты группы из базы и уже оценённые; сохраняется целиком. Файл `ФИО | Результат` (CSV/XLSX) разбирается на сервере и только подставляется в ведомость: сохраняет её преподаватель после проверки, поэтому отдельной загрузки с отменой нет. Результаты вносятся в день проведения или позже. Группу с результатами нельзя убрать из работы, дисциплину работы с результатами — сменить.
  - Средние и статистики считаются только по баллам; отметки и пропуски показаны отдельно (FR-074). Сравнение групп по работе — описательные статистики `descriptiveStats` по каждой группе. По дисциплине у студента — средний балл входного и итогового контроля и разность («входной → итоговый»).
  - Результаты выводятся в профиль студента (вкладка «Диагностика», рядом с оценками за семестр, с графиком динамики), в «Мои достижения» студента (свои результаты), в конструктор ИОТ (входной контроль по выбранной дисциплине — справочно, сложность не ограничивает, FR-033) и в показатели исследования: для каждой дисциплины с контрольными работами — показатель «Контрольные работы: <дисциплина>» с «до» = входной контроль и «после» = итоговый; он попадает в сводную и широкую обезличенную выгрузку (FR-071, FR-075).
  - Доступ: просмотр — сотрудникам с доступом к группе (`students.read`); создание, изменение и ввод результатов — администратору и преподавателю пары группа — дисциплина (`grades.manage`, FR-002); изменения пишутся в аудит (`control_work.*`, `control_results.saved`).
- **Последствия.** Текущий контроль хранится теми же работами с видом «текущий»; оценки за задания ИОТ остаются в `academic_results` и в сравнение ЭГ и КГ не входят. Вкладка «Успеваемость» раздела «Дисциплины» больше не существует — оценки за семестр открываются в «Академических достижениях».

## ADR-036. Сводный статистический анализ педагогического эксперимента

- **Контекст.** Этап 29 (запрос заказчика 2026-10-30): для магистерской ВКР нужна групповая аналитика эксперимента по всем участникам (20 ЭГ и 20 КГ): сравнение первичного и повторного замеров по каждой шкале методик Т. А. Ильиной, А. А. Реана — В. А. Якунина и В. И. Моросановой, анализ успеваемости (входной, текущий, итоговый контроль), средние, медианы, стандартные отклонения, изменения, доли студентов с положительной, отрицательной и нулевой динамикой, критерии Вилкоксона, Манна — Уитни и Спирмена с p-значениями и размерами эффекта, таблицы и графики для ВКР. Критерии значились в п. 10.2 ТЗ (вне MVP, огр. 6) — заказчик запросил их явно. Баллы разных методик нельзя объединять в один показатель; мотивация, саморегуляция и академические достижения показываются раздельно; перед расчётом нужны проверки полноты пар, версии методики и шкал.
- **Решение.**
  - Критерии реализованы чистыми функциями в `packages/shared/src/statistical-tests.ts` без новых зависимостей и совпадают с R/SciPy: критерий знаковых рангов Вилкоксона (нулевые разности отбрасываются; T — меньшая сумма рангов), Манна — Уитни (U — меньшее из U₁, U₂), ранговая корреляция Спирмена (средние ранги; p по t-распределению с n − 2 степенями свободы). p-значение — точное распределение при n < 50 без совпадений и нулей, иначе нормальное приближение с поправками на непрерывность и совпадения. Размер эффекта — r = |Z|/√N (для Спирмена — ρ), градации Дж. Коэна 0,1 / 0,3 / 0,5. Критерии считаются при 5 и более наблюдениях (парах) в группе, иначе — «не рассчитывается» с причиной. Уровень значимости 0,05. Эталоны тестов — SciPy 1.18 и примеры справки R.
  - Анализ (`buildResearchAnalysis` в `packages/shared/src/research-analysis.ts`) строится из уже собранных данных исследования (ADR-023, ADR-033, ADR-035): каждая шкала каждой методики и каждый показатель успеваемости и наблюдений — отдельная переменная, без суммирования. Раздел переменной определяется диагностическим направлением методики: «Учебная мотивация» → «Мотивация», «Саморегуляция» → «Саморегуляция», прочие — «Другие методики»; успеваемость (средний балл за семестр, контрольные работы) — «Академические достижения»; оценки на занятиях — «Педагогические наблюдения». Направление методики можно изменить в её карточке, результаты при этом не пересчитываются.
  - «До» и «после» для методики — первый и последний замер исследования (обычно первичный и повторный). Проверки перед расчётом: тип замеров (первичный → повторный, иначе предупреждение); версия методики одна или пара утверждена сопоставимой (иначе изменение и критерии не считаются, FR-072); шкала с тем же кодом есть в обеих версиях и имеет тот же способ расчёта (сумма/среднее), разное название — предупреждение; полнота пар в каждой группе (неполные пары исключаются попарно, меньше 5 пар — критерии не считаются); для успеваемости и наблюдений — выбраны оба семестра или периода. Демо-методика помечается предупреждением.
  - По каждой переменной и группе — описательные статистики «до», «после» и изменения, число и доля студентов с ростом, без изменений и со снижением, критерий Вилкоксона; между ЭГ и КГ — критерий Манна — Уитни «до» (исходная равноценность), «после» и по изменению. Корреляции Спирмена — между переменными по значениям «до», «после» или по изменению (только сопоставимые пары), для всех участников, ЭГ или КГ.
  - Текущий контроль: в данные исследования добавлены ряд контрольных работ каждой дисциплины по датам (описательные статистики ЭГ и КГ по каждой работе) и средний балл текущего контроля участника; в сравнение «до/после» текущий контроль не входит (ADR-035), в широкую таблицу — отдельной колонкой.
  - Интерфейс: блок «Статистический анализ эксперимента» в «Данных исследования» (меню не меняется): сводные показатели, разделы с графиками (средние «до/после» по шкалам, доли динамики, ряд контрольных работ), карточки переменных с проверками, выводом обычным языком и таблицами, матрица корреляций. Расчёт в браузере и в выгрузке выполняют одни и те же функции shared.
  - Выгрузка: набор «Статистический анализ: таблицы для ВКР» (`dataset=analysis`) — пять таблиц (проверки, внутригрупповой анализ, ЭГ и КГ, корреляции, контрольные работы); в XLSX — отдельные листы, в CSV — разделы подряд с заголовками таблиц. Только коды и ЭГ/КГ, запись в аудит, как у остальных наборов (FR-075).
- **Последствия.** Схема БД не меняется. Методика В. И. Моросановой появится в разделе «Саморегуляция» после внесения через конструктор с этим направлением; до тех пор раздел показывает «Нет данных». Интерпретация результатов (выводы ВКР) остаётся за исследователем: система показывает рассчитанные значения и не делает выводов о причинности.
