# Автоматическое обновление при пуше в `main`

Сервер получает код из закрытого репозитория GitHub по deploy key (ключ только для чтения) и обновляется после каждого пуша в ветку `main`. Обновление выполняет тот же `scripts/deploy.sh`, что и при ручном обновлении ([update.md](update.md)), в режиме без вопросов. Файл `docker-compose.prod.yml` не меняется: образы собираются на сервере из полученного кода.

## Однократная настройка сервера

1. Закрытый ключ deploy key лежит на сервере у пользователя, от имени которого запускается обновление (например, `/home/iot/.ssh/iot_deploy`, права `600`). Открытый ключ добавлен в репозиторий: Settings → Deploy keys, без права записи.
2. В `~/.ssh/config` этого пользователя:

   ```
   Host github.com
     IdentityFile ~/.ssh/iot_deploy
     IdentitiesOnly yes
   ```

3. Репозиторий клонируется по SSH (не по HTTPS — с HTTPS ключ не используется):

   ```sh
   git clone -b main git@github.com:Homka-1/kpvk-iot.git /opt/iot
   ```

   В уже существующей копии: `git remote set-url origin git@github.com:Homka-1/kpvk-iot.git`. Проверка: `git -C /opt/iot fetch origin`.

4. Первая установка — вручную, с выбором сертификата и созданием администратора ([install.md](install.md)):

   ```sh
   /opt/iot/scripts/deploy.sh --mode install
   ```

   Пользователь, от имени которого идёт обновление, должен входить в группу `docker` и иметь права записи в `/opt/iot`.

## Команда обновления

На каждое событие пуша в `main` выполняется:

```sh
/opt/iot/scripts/deploy.sh --mode update --ref main --yes
```

Скрипт:

- ждёт завершения предыдущего запуска (блокировка `.deploy.lock`, до 30 минут), поэтому пуши подряд обновляют стенд по очереди;
- делает резервную копию базы и файлов до смены кода; если контейнер `backup` не работает, обновление **отменяется** — без копии автоматическое обновление не выполняется;
- получает `main` из `origin` только перемоткой вперёд (`--ff-only`) и отказывается работать, если в `/opt/iot` есть незафиксированные изменения отслеживаемых файлов;
- собирает образы с меткой `ГГГГММДД-ЧЧММ-<коммит>`, перезапускает контейнеры (API применяет новые миграции) и проверяет `https://localhost/api/health`;
- после успешного обновления удаляет старые образы `iot-api`, `iot-web`, `iot-backup`, кроме текущей и предыдущей версии (предыдущая нужна для отката), и кэш сборки старше 7 дней.

Код возврата `0` — обновление прошло; любой другой — нет, причина в выводе скрипта. При ошибке выводятся журнал API, имя резервной копии и прежняя `IOT_VERSION`. Откат автоматически не выполняется: восстановление копии удаляет данные, внесённые после неё, решение принимает администратор ([update.md](update.md), раздел «Откат»). Сохраняйте вывод запусков в журнал и настройте оповещение при ненулевом коде возврата.

## Как запускать по событию пуша

Способ выбирает администратор сервера; для приложения важен только вызов команды выше. Если сервер находится в локальной сети колледжа и недоступен из интернета (вебхук GitHub до него не дойдёт), подходит опрос репозитория по таймеру systemd.

`/etc/systemd/system/iot-autodeploy.service`:

```ini
[Unit]
Description=Обновление ИОТ из ветки main
After=docker.service

[Service]
Type=oneshot
User=iot
WorkingDirectory=/opt/iot
ExecStart=/bin/sh -c '[ "$(git ls-remote origin refs/heads/main | cut -f1)" = "$(git rev-parse HEAD)" ] || scripts/deploy.sh --mode update --ref main --yes'
```

`/etc/systemd/system/iot-autodeploy.timer`:

```ini
[Unit]
Description=Проверка новых коммитов ИОТ каждые 5 минут

[Timer]
OnBootSec=2min
OnUnitActiveSec=5min

[Install]
WantedBy=timers.target
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now iot-autodeploy.timer
journalctl -u iot-autodeploy.service   # журнал запусков
```

Неудачный запуск не повторяется до следующего коммита в `main`. После устранения причины запустите обновление вручную командой из раздела «Команда обновления».

## Что учитывать разработчикам

- Каждый пуш в `main` попадает на рабочий сервер. Перед пушем должны проходить `pnpm lint`, `pnpm typecheck`, `pnpm test`.
- Миграции применяются автоматически и должны сохранять данные (NFR-007). Миграцию, которая удаляет или переименовывает столбцы с данными, согласуйте с администратором до пуша.
- Новые переменные окружения в `.env.prod.example` не попадают в `.env.prod` сами: сообщите администратору до пуша, иначе контейнеры не запустятся и обновление завершится ошибкой.
