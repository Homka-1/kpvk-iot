# Обновление

Обновление до новой версии без потери данных (NFR-007). Данные хранятся в томах `pgdata` и `files`, которые при пересоздании контейнеров сохраняются. Структура базы меняется только миграциями Prisma: при старте API применяет новые миграции по порядку, уже применённые пропускает. Миграции проекта не удаляют данные, каждая проверяется на пустой базе и на базе предыдущего этапа.

## Порядок

Выполняйте в согласованное окно обслуживания. Пользователи на время перезапуска API (до минуты) увидят сообщение об ошибке соединения.

```sh
cd /opt/iot
export COMPOSE_FILE=docker-compose.prod.yml COMPOSE_ENV_FILES=.env.prod

# 1. Резервная копия перед обновлением (обязательно).
docker compose exec backup backup.sh

# 2. Новый код.
git fetch
git checkout <метка новой версии>

# 3. Новая метка образов в .env.prod (например, дата), чтобы старые образы остались для отката.
#    IOT_VERSION=2026-11-01

# 4. Сборка и перезапуск. API применит новые миграции при старте.
docker compose up -d --build --wait

# 5. Проверка.
docker compose ps
docker compose logs api --tail 50
```

Если миграция не применилась, API не запускается (контейнер перезапускается, `ps` показывает `unhealthy` или `restarting`), а в журнале `docker compose logs api` видна причина. Prisma отмечает такую миграцию как неудачную и не применяет следующие. Самый надёжный выход — восстановить копию шага 1 и вернуть прежнюю версию (раздел «Откат»), затем разобраться с причиной на тестовом стенде.

Сравните `.env.prod.example` новой версии со своим `.env.prod`: в описании выпуска указываются новые переменные, если они появились.

## Откат

Откат кода на старую версию возможен, только если новая версия не добавила миграций. Если миграции были применены, старый код может не работать с новой структурой базы — тогда откат выполняется вместе с восстановлением резервной копии, сделанной на шаге 1:

```sh
git checkout <метка прежней версии>
# В .env.prod вернуть прежнее IOT_VERSION (образы прежней версии ещё на сервере).
docker compose stop api
docker compose exec backup restore.sh <имя копии шага 1>
docker compose up -d --wait
```

Данные, внесённые пользователями после копии шага 1, при таком откате теряются, поэтому сначала стоит выяснить причину сбоя.

## Обслуживание

- Свободное место: `df -h`, `docker system df`. Старые образы удаляются командой `docker image prune` (образы работающих контейнеров не затрагиваются).
- Журналы: `docker compose logs <сервис>`; Docker хранит до 50 МБ журнала на контейнер.
- Остановка без удаления данных: `docker compose down`. Команда `docker compose down -v` **удаляет тома с базой и файлами** — на рабочем сервере её не используют.
