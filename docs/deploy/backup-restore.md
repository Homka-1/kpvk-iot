# Резервное копирование и восстановление

Резервное копирование и проверенное восстановление обязательны по п. 8.3 ТЗ; проверка восстановления — критерий AT-13.

## Что входит в копию

Контейнер `backup` по расписанию `BACKUP_SCHEDULE` (по умолчанию ежедневно в 02:30 по `TZ`) создаёт каталог `<ГГГГММДД-ЧЧММСС>` в каталоге копий (`BACKUP_HOST_DIR`, по умолчанию `./backups`):

| Файл           | Содержимое                                                                          |
| -------------- | ----------------------------------------------------------------------------------- |
| `db.dump`      | Дамп базы `pg_dump` в формате custom: все таблицы, включая журнал аудита и миграций |
| `files.tar.gz` | Все загруженные файлы библиотеки и сдачи заданий (том `files`)                      |
| `info.txt`     | Время создания, имя базы, последняя применённая миграция                            |
| `SHA256SUMS`   | Контрольные суммы трёх файлов выше                                                  |

- Копия пишется в каталог `*.partial` и получает окончательное имя только после успешного завершения. Незавершённая копия не выглядит готовой и удаляется при следующем запуске.
- После каждой копии остаются `BACKUP_KEEP` (по умолчанию 14) последних копий, более старые удаляются.
- Файлы копий доступны только root (`umask 077`): в них персональные данные.
- Журнал копирования: `docker compose logs backup`.

Копия не заменяет хранение на другом носителе: если отказал диск сервера, копии на нём пропадут вместе с данными. Настройте перенос каталога копий на другой сервер или носитель (rsync, сетевое хранилище колледжа) средствами сисадмина.

Помимо копий данных храните отдельно `.env.prod` и сертификат.

## Копия вручную

```sh
cd /opt/iot
export COMPOSE_FILE=docker-compose.standalone.yml COMPOSE_ENV_FILES=.env.prod
docker compose exec backup backup.sh
```

Последняя строка вывода — имя созданной копии.

## Восстановление

Восстановление полностью заменяет содержимое базы и загруженные файлы содержимым копии.

```sh
cd /opt/iot
export COMPOSE_FILE=docker-compose.standalone.yml COMPOSE_ENV_FILES=.env.prod

# 1. Остановить API: к базе не должно быть подключений.
docker compose stop api

# 2. Восстановить копию по имени (или latest — самую новую).
docker compose exec backup restore.sh 20261020-023000

# 3. Запустить API.
docker compose up -d --wait
```

Скрипт `restore.sh`:

1. проверяет контрольные суммы копии и ничего не меняет, если копия повреждена;
2. отказывается работать, пока к базе подключены другие клиенты;
3. пересоздаёт схему базы и загружает дамп;
4. заменяет содержимое тома `files` архивом из копии.

Если копия сделана более старой версией приложения, после восстановления API при старте применит недостающие миграции.

### Восстановление на новом сервере

1. Установите приложение по [install.md](install.md) той же или более новой версии, с сохранённым `.env.prod` (шаг 5 «Первая учётная запись» не нужен).
2. Скопируйте каталог копии в `BACKUP_HOST_DIR` нового сервера.
3. Выполните шаги восстановления выше.

## Проверка восстановления (AT-13)

Автоматизированный тест повторяет всю процедуру на отдельном стенде:

```sh
pnpm install
pnpm test:restore
```

Тест (`docker/test/restore.test.mts`) поднимает рабочую сборку отдельным проектом Docker Compose `iot-at13` на портах 18080/18443 с самоподписанным сертификатом, создаёт через API администратора, преподавателя, группу и загружает файл, делает копию контейнером `backup`, удаляет стенд вместе с томами, поднимает пустой стенд, восстанавливает копию и проверяет: учётные записи входят со своими паролями, группа на месте, файл совпадает побайтно, запись журнала аудита сохранилась. После теста стенд и его тома удаляются; рабочие тома других проектов не затрагиваются. Время — около 4 минут (с собранными образами).

На сервере колледжа рекомендуется раз в квартал вручную восстанавливать свежую копию на тестовом стенде (отдельный проект Compose, например `-p iot-restore-check`, со своими портами) и проверять вход и данные.
