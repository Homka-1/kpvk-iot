# Нагрузочное тестирование (NFR-001, NFR-002)

Цель — подтвердить, что в пилотной конфигурации система обслуживает не менее 50 одновременных активных пользователей (NFR-001), а основные экраны открываются не дольше 3 секунд (NFR-002).

## Методика

- **Инструмент:** k6 2.3.0 (образ `grafana/k6:2.3.0`, ставить k6 на машину не нужно).
- **Сценарий:** `apps/api/test/load/screens.k6.js`. 50 виртуальных пользователей работают одновременно всё время теста: 10 преподавателей и 40 студентов. Каждый по кругу открывает основные экраны своей роли с паузой 2–5 секунд между ними, как человек.
- **Экран** — набор запросов API, который интерфейс отправляет при открытии раздела. Запросы экрана идут параллельно, время экрана — до последнего ответа. Это время и сравнивается с порогом 3 с.

| Роль          | Экран               | Запросы API                                                                                  |
| ------------- | ------------------- | -------------------------------------------------------------------------------------------- |
| Преподаватель | Главная панель      | `GET /auth/me`, `GET /dashboard`, `GET /notifications`                                       |
| Преподаватель | Студенты            | `GET /students?groupId=…`, `GET /groups`                                                     |
| Преподаватель | Профиль студента    | `GET /students/:id/profile`, `/students/:id/diagnostics`, `/students/:id/motivation-profile` |
| Преподаватель | Мониторинг          | `GET /monitoring`                                                                            |
| Преподаватель | Аналитика           | `GET /analytics`                                                                             |
| Преподаватель | Задания на проверку | `GET /student-assignments/review`                                                            |
| Студент       | Главная студента    | `GET /auth/me`, `/cabinet/trajectories`, `/cabinet/assignments`, `/notifications`            |
| Студент       | Моя траектория      | `GET /cabinet/trajectories`                                                                  |
| Студент       | Мои задания         | `GET /cabinet/assignments`                                                                   |
| Студент       | Диагностика         | `GET /cabinet/diagnostics`                                                                   |
| Студент       | Мой профиль         | `GET /cabinet/profile`                                                                       |

- **Пороги (критерии прохождения):** для каждого экрана 95-й процентиль времени ≤ 3000 мс; доля ошибочных ответов < 1 %. При нарушении любого порога k6 завершается с ненулевым кодом.
- **Данные:** объём пилота — две группы по 25 студентов (ориентир AT-01 — по 20). Скрипт `apps/api/test/load/prepare-data.ts` создаёт их через API: у каждого студента учётная запись, утверждённая ИОТ из 5 этапов с контрольными точками и тремя заданиями, результат диагностики (ввод бланка) и отправленный ответ на первое задание. Один преподаватель закреплён за обеими группами — это худший случай для экранов преподавателя (в области данных все 50 студентов).
- **Окружение:** API собран и запущен в режиме `production` (`node dist/main.js`), PostgreSQL 16 в Docker. Генератор нагрузки, API и база — на одной машине, то есть условия жёстче, чем на отдельном сервере.

## Как повторить

Используйте отдельную базу: скрипт создаёт данные, которые не нужны ни в разработке, ни в рабочей системе.

1. Создать базу и файл окружения нагрузочного стенда (на основе `.env`):

   ```sh
   docker exec <контейнер postgres> psql -U iot -d iot_dev -c "CREATE DATABASE iot_load"
   # .env.load: DATABASE_URL с базой iot_load, NODE_ENV=production, API_PORT=3100,
   # LOGIN_RATE_LIMIT=100000 (все 50 пользователей входят с одного адреса за секунду)
   ```

2. Собрать API, применить миграции, заполнить сид и запустить API:

   ```sh
   pnpm build:shared && pnpm --filter @iot/api build
   cd apps/api
   ENV_FILE=.env.load npx prisma migrate deploy
   ENV_FILE=.env.load npx prisma db seed
   ENV_FILE=.env.load node dist/main.js
   ```

3. В другом терминале подготовить данные и запустить тест:

   ```sh
   ENV_FILE=.env.load LOAD_API_URL=http://localhost:3100 pnpm test:load:prepare
   LOAD_API_URL=http://localhost:3100 pnpm test:load
   ```

   Учётные записи для k6 записываются в `apps/api/test/load/accounts.local.json` (файл не коммитится). Длительность меняется переменной `LOAD_DURATION` (по умолчанию `3m`).

`LOGIN_RATE_LIMIT` повышается только на нагрузочном стенде: в рабочей конфигурации ограничение частоты входа с одного адреса (п. 8.3) остаётся.

## Результаты

**Дата:** 2026-10-20. **Версия:** ветка этапа 19. **Машина:** Intel Core i5-7200U (2 ядра, 4 потока), 8 ГБ ОЗУ — близко к ориентиру для пилота из п. 8.2 ТЗ (2–4 vCPU, 8 ГБ).

- Запросов: 4441, ошибочных — 0 (0,00 %); проверок «все ответы экрана — 200»: 2665 из 2665.
- Хвост p95 у двух главных экранов — первый одновременный заход: все 50 пользователей открывают главную в одну и ту же секунду (около 180 параллельных запросов). Даже этот пик — до 1,9 с, ниже порога. В установившемся режиме медианы экранов — 9–77 мс.

**Итог:** NFR-001 и NFR-002 подтверждены для пилотного объёма.

### Повтор на приёмочном стенде (этап 20)

**Дата:** 2026-10-20. Данные — приёмочный стенд (`pnpm acceptance:stand`): две группы по 20 студентов (AT-01), утверждённые ИОТ, диагностика, исследование. API в режиме `development`, та же машина. Файл учётных записей для k6 собран из `apps/web/e2e/acceptance/stand.local.json`, запуск — `LOAD_API_URL=http://localhost:3200 pnpm test:load`.

Прогон 3 минуты, 50 одновременных пользователей (10 преподавателей, 40 студентов): 2676 проверок, ошибок 0 %. 95-й процентиль по экранам: главная панель преподавателя 1,36 с, главная студента 1,64 с, остальные экраны — от 22 до 80 мс. Все пороги выполнены.

## Когда повторять

После изменений в мониторинге, главной панели, аналитике и кабинете студента, а также перед приёмкой на сервере колледжа (на его оборудовании результаты нужно получить заново).
